01

SAP system basics

Basics

Why it's asked: warm-up questions. Answering them crisply shows she understands what runs underneath her code.

1.1 What SAP and ABAP are

SAP S/4HANA is an ERP system: one integrated software package that runs a company's core business. That means finance (FI), controlling (CO), sales and distribution (SD), materials management (MM), production planning (PP), quality, plant maintenance, HR and more, all sharing one database. When a salesperson creates a sales order, the same data flows into delivery, billing and accounting without re-entry.

SAP ships standard programs for all of this. Companies always need something extra: a special report, an interface to a bank or a legacy system, an extra validation, a company-branded invoice, an approval process. ABAP (Advanced Business Application Programming) is SAP's own language for building those extras and for changing standard behaviour safely. An ABAP developer writes code that runs inside the SAP system, right next to the business data.

Say it in the interview: "SAP gives the standard business processes; as an ABAP developer I build the custom objects that close the gap between standard SAP and the client's exact requirement, using the RICEFW categories."

1.2 Three-tier architecture in detail

Presentation layer SAP GUI | Fiori Launchpad in a browser | external apps │ (user requests) Application layer Dispatcher ─► Work processes (D, B, V, E, S) ─ ABAP programs run here │ (Open SQL translated to DB SQL by the database interface) Database layer SAP HANA (S/4HANA) ─ tables, CDS views, procedures

Presentation layer. This is only the screen. SAP GUI is the classic Windows client where you enter T-codes. Fiori is the modern browser UI built on SAPUI5, which talks to the back end through OData services. No business logic runs here.

Application layer. One or more application servers run the ABAP runtime. Each server has a dispatcher that receives user requests, puts them in a queue, and hands each request to a free work process. A work process is an operating-system process that actually executes your ABAP code. Because there are a limited number of work processes, long-running dialog steps block other users, which is why SAP kills dialog steps after a timeout (parameter rdisp/max_wprun_time, often 10–20 minutes) with dump TIME_OUT.

Database layer. Stores all data. ABAP code uses Open SQL, which the database interface translates into the native SQL of the actual database. That is why the same ABAP program runs on any database SAP supports. In S/4HANA the database is always SAP HANA, an in-memory column-store database.

Other components you should be able to name: the message server (load balancing between application servers and communication), the gateway (RFC communication with other systems), and the ICM (Internet Communication Manager, which handles HTTP requests such as OData and web services).

1.3 Work processes

A dialog step is everything that happens between two screens: the user presses a key, the work process runs the PAI of one screen and the PBO of the next, then the work process is released. Your program does not keep a work process for its whole lifetime, only for each step. That has a big consequence: a database commit happens implicitly at the end of every dialog step (more in module 12).

Common mistake: running a huge data extraction in dialog mode. It times out. Run heavy reports in background (F9 or SM36), where there is no dialog timeout.

1.4 Clients, systems and the landscape

A client is a self-contained unit inside one SAP system with its own business data, users and configuration. Client numbers are three digits, e.g. 100 for development, 200 for unit testing. Almost every application table has MANDT (client) as its first key field. Open SQL adds the current client to every query automatically, so you never write WHERE mandt = sy-mandt.

Client-dependent: business data and most configuration, such as customers in KNA1 or a company's own Z customizing table with MANDT. Client-independent (cross-client): repository objects, meaning programs, classes, function modules, DDIC definitions, Smart Forms, and tables without MANDT. If you change a program in client 100 it changes for every client in that system.

A typical landscape has three systems:

  1. DEV (development): developers write and unit-test code here.
  2. QAS (quality): functional consultants and business users test integration and acceptance.
  3. PRD (production): the live system. Nobody develops here; changes only arrive by transport.

Some projects also have a sandbox, a pre-production system, or a separate training client.

1.5 Transport requests step by step

Every change to a repository object in DEV is recorded in a transport request (TR). The TR is how code travels from DEV to QAS and PRD.

  1. When you save a new or changed object, SAP asks for a package and a request. Choose an existing request or create one.
  2. A request contains tasks, one per developer. Your object is recorded in your task.
  3. When done and unit-tested, you release your task in SE09/SE10, then the request owner releases the request.
  4. Releasing exports the objects to the file system. The Basis team (or a tool like ChaRM or STMS QA approval) then imports the request into QAS, and later into PRD, in STMS.

Workbench requests carry client-independent repository objects (programs, tables, classes). Customizing requests carry client-specific configuration entries made in SPRO or SM30. A Transport of Copies (type ToC) is often used to move a snapshot to QAS for testing without releasing the original request.

Common mistake: transporting a program but forgetting the data element, table or message class it depends on, which sits in a different TR. The import into QAS then fails or the program dumps. Always check object dependencies, and import in the correct sequence.

Packages group related objects (e.g. ZSD_REPORTS) and are linked to a transport layer, which decides the transport route. $TMP is the local package: objects there can never be transported and are only for experiments.

Customer namespace: custom objects must start with Z or Y (or a registered namespace like /ACME/). This protects them from being overwritten in upgrades.

1.7 How a development task flows in a real project

  1. The functional consultant writes a Functional Specification (FS): the business need, rules, screens, sample data.
  2. The developer reviews it, asks questions, and writes a Technical Specification (TS): objects to create, logic, tables, error handling.
  3. Development in DEV, following naming conventions and coding standards, with a transport request.
  4. Code review by a senior developer, plus Code Inspector or ATC checks with no priority 1 or 2 errors.
  5. Unit testing by the developer, documented in a unit test document.
  6. Release and transport to QAS. Functional testing, integration testing (SIT) and user acceptance testing (UAT).
  7. Transport to PRD after approval, then hypercare support after go-live.

Project types you may be asked about: implementation (new SAP rollout), rollout (an existing template extended to a new country), upgrade/migration (ECC to S/4HANA conversion), and support (ticket-based work on a live system with SLAs and incident, problem and change tickets).

Say it in the interview: "I receive the FS from the functional consultant, clarify the gaps, prepare the TS, develop in DEV under a transport, run ATC, get the code reviewed, unit test, and support SIT and UAT in QAS before the move to production."

1.8 Daily T-codes for an ABAP developer

A T-code is a shortcut that starts a transaction. /n plus a T-code ends the current transaction and starts the new one, /o opens it in a new window, and /h switches on the debugger.

SE38 ABAP editor, SE80 object navigator, SE11 dictionary, SE37 function builder, SE24 class builder, SE91 messages, SE93 create T-codes, SE09 transports, ST22 dumps, SM37 jobs, SM12 locks. In S/4HANA projects, many developers also use Eclipse with ABAP Development Tools (ADT), which is required for CDS views, AMDP and RAP.

Useful tables to know by heart, because interviewers like them: MARA (material general), MARC (material plant), MARD (storage location stock), KNA1 (customer), LFA1 (vendor), VBAK/VBAP (sales order header/item), LIKP/LIPS (delivery), VBRK/VBRP (billing), EKKO/EKPO (purchase order), BKPF/BSEG (accounting document), ACDOCA (universal journal in S/4), T001 (company codes), TADIR (repository object directory), BUT000 (business partner).

Interview questions

Explain SAP's three-tier architecture.

The presentation layer is the UI (SAP GUI or Fiori in a browser). The application layer runs ABAP programs on one or more application servers, with a dispatcher assigning requests to work processes. The database layer stores all data and, in S/4HANA, is always SAP HANA. Separating them lets each layer scale independently.

What types of work processes exist?

Dialog for interactive requests, Background for scheduled jobs (SM36/SM37), Update for database changes made via update function modules, Enqueue for managing SAP locks, and Spool for print output. SM50 shows them on one server, SM66 across servers.

What is a transport request and how does it move?

A container that records changed objects. Each developer works in a task under the request. Tasks are released first, then the request, in SE09/SE10. Basis imports the released request into QA and PRD through STMS. Workbench requests carry repository objects (programs, tables). Customizing requests carry client-specific configuration.

What is the difference between client-dependent and client-independent objects?

Client-dependent data has MANDT as its first key field and is visible only in its client (business data, most configuration). Client-independent objects are shared across all clients: ABAP programs, DDIC definitions, Smart Forms, and tables without a MANDT field.

What is a dialog step and why does it matter for developers?

A dialog step is the processing between two screens: PAI of the current screen plus PBO of the next. The work process is assigned only for that step and then released, and an implicit database commit happens at its end. So you can't keep a database transaction open across screens, which is why SAP uses update function modules and SAP locks to build a business transaction (SAP LUW) across several steps.

Why must custom objects start with Z or Y?

Z and Y are the customer namespace. SAP never delivers objects with these names, so upgrades and support packages won't overwrite them. Larger customers or partners can register their own namespace like /ABC/.

What is the difference between a functional and technical specification?

The functional spec (written by the functional consultant) describes what the business needs: process, rules, fields, sample inputs and outputs. The technical spec (written by the developer) describes how it will be built: objects, tables read and written, program flow, error handling, performance considerations and test cases.

What is the $TMP package?

The local package. Objects saved there need no transport request and can never be transported, so it is only for prototypes and tests. To move an object out later, change its package assignment via Goto → Object directory entry.

ABAP Dictionary (SE11)

Basics

JD link: "application design principles". Good table design is where design starts. Expect 3–5 questions here in almost every ABAP interview.

2.1 What the ABAP Dictionary is

The ABAP Dictionary (DDIC, transaction SE11) is the central place where SAP stores the definitions of all data: tables, views, data types, search helps and lock objects. When you activate a table in SE11, SAP creates the real table in the database. Every program that uses a DDIC type sees the same definition, so a change in one place is reflected everywhere. That is the main reason the DDIC exists: one consistent, reusable definition of data for the whole system.

Objects you create in SE11: database tables, views, data types (data elements, structures, table types), type groups, domains, search helps and lock objects.

2.2 Domain and data element: the two-level type concept

SAP describes every table field on two levels.

Domain = the technical level. It defines:

  • Data type from the built-in DDIC types: CHAR (text), NUMC (digits stored as text, e.g. order numbers), DATS (date YYYYMMDD), TIMS (time HHMMSS), DEC (packed decimal), CURR (amount, must point to a currency field of type CUKY), QUAN (quantity, must point to a unit field of type UNIT), INT4, STRING, RAW, CLNT (client).
  • Length and decimals.
  • Output characteristics: lowercase allowed, sign, and a conversion routine such as ALPHA, which adds leading zeros (so customer 4711 is stored as 0000004711). The routine names generate function modules like CONVERSION_EXIT_ALPHA_INPUT and ..._OUTPUT.
  • Value range: fixed values (e.g. A = Active, I = Inactive), intervals, or a value table.

Data element = the semantic level. It defines the business meaning:

  • The type: a domain (most common), a built-in type directly, or a reference type.
  • Field labels: short, medium, long and heading texts. These are what users see as column headers on screens and ALV reports.
  • Documentation: the F1 help text.
  • Optionally a search help and a parameter ID (SET/GET parameter, so a field is pre-filled from the user's memory, e.g. AUN for sales order).

Example: domain ZD_STATUS (CHAR 1, fixed values A/I/D). Two data elements use it: ZE_ORDER_STATUS ("Order status") and ZE_ITEM_STATUS ("Item status"). Same technical definition, different meaning and labels.

Say it in the interview: "A domain gives the technical properties: type, length and allowed values. A data element gives the business meaning: labels and F1 help. Many data elements can share one domain."

2.3 Creating a custom table, step by step

  1. Create the domains you need (or reuse standard ones like KUNNR, MATNR), then the data elements. Activate both.
  2. SE11 → Database table → ZSD_ORDER_LOG → Create. Enter a short description.
  3. Delivery and Maintenance tab: choose the delivery class (usually A for application data, C for customizing) and Data Browser/Table View Maintenance: "Display/Maintenance Allowed" if you want SM30 maintenance.
  4. Fields tab: first field MANDT with data element MANDT, marked as key. Then your key fields, then non-key fields. Tick Key for the primary key and Initial values where needed.
  5. Currency/Quantity fields tab: for every CURR field enter the reference table and CUKY field. For every QUAN field, the UNIT field. Activation fails without this.
  6. Technical settings (button): data class (APPL0 master data, APPL1 transaction data, APPL2 organisation/customizing), size category (expected number of rows), buffering, and log data changes.
  7. Enhancement category (Extras menu): e.g. "Can be enhanced (character-type or numeric)". Required since 7.0 and controls whether appends are allowed.
  8. Activate. The database table is created. Check it in SE14 (database utility) if anything goes wrong.
Common mistake: changing the key or shortening a field on a table that already has data. That requires a table conversion in SE14, which can take hours on large tables and can lose data. Design the key carefully from the start.

2.4 Table types

Transparent table: exactly one database table with the same name and fields. All application data lives in these. In S/4HANA almost everything is transparent.

Pooled table: (old) many small SAP tables stored together in one database table pool. Cluster table: (old) several logically related tables stored together in one cluster, e.g. BSEG was in cluster RFBLG in ECC. You couldn't use joins on them. In S/4HANA both were converted to transparent tables, which is why BSEG can now be joined.

Global temporary tables (GTT) exist for temporary data inside one database LUW, and structures (no data, just a layout used in programs and screens).

2.6 Technical settings and buffering

Data class decides the physical storage area (mostly relevant on older databases). Size category (0 to 9) estimates the number of rows, used to reserve space.

Table buffering keeps a copy of table data in the application server's memory, so reads don't go to the database at all. That is around 10–100 times faster.

  • Single-record buffering: only the rows actually read with SELECT SINGLE on the full key are buffered. Good for large tables where only a few rows are read often.
  • Generic area buffering: when one row is read, all rows with the same values in the first n key fields are loaded. E.g. generic key 2 on (MANDT, BUKRS, ...) buffers everything for one company code.
  • Full buffering: the whole table is loaded at first access. Good for small tables like T001.

The buffer is synchronised across application servers asynchronously (table DDLOG, roughly every 1–2 minutes), so another server may briefly see old data. That's why you never buffer frequently changed data.

The buffer is bypassed by: BYPASSING BUFFER, SELECT ... FOR UPDATE, aggregate functions, DISTINCT, joins, subqueries, ORDER BY on non-key fields, IS NULL, native SQL, and SELECT SINGLE without the full key on a single-record-buffered table.

2.7 Structures, table types and the TYPE reference

A structure in SE11 is a list of fields without a database table, used for screens, interfaces and program variables. A table type describes an internal table: its line type (often a structure), its table kind (standard, sorted, hashed) and its key. You need table types for function module and method parameters that pass tables.

DATA ls_order  TYPE zsd_order_log.        " structure based on a table
DATA lt_orders TYPE zsd_tt_order_log.     " internal table based on a DDIC table type

2.8 Include structure vs append structure

Include structure (.INCLUDE in the field list): you insert an existing structure into a table or structure. The same include can be reused in many tables, e.g. a standard address block. You can put it anywhere in the field list and give it a group name or suffix.

Append structure: created for exactly one table and always added at its end. Its purpose is to add custom fields to SAP standard tables without a modification. The table itself is not changed, so the append survives upgrades. Custom field names must start with ZZ or YY to avoid clashes with fields SAP may add later.

Example: to add a "Sales channel" field to sales order header table VBAK, create append structure ZAVBAK with field ZZSALES_CHANNEL. SAP standard (and BAPI extension structures like VBAKKOZ) can then carry it.

Limits: appends are not allowed on pooled or cluster tables, or on tables with a long field (LCHR or LRAW) at the end, and they depend on the table's enhancement category.

Customizing include (CI_ includes) is a special include that SAP leaves empty in standard tables for customers to fill, e.g. CI_EKPODB for purchase order items.

2.9 Foreign keys, check tables, value tables and text tables

A foreign key links a field in one table (the foreign key table) to the primary key of another table (the check table). When a user types a value on a screen, SAP checks that the value exists in the check table and shows an error if not. Example: field LAND1 in KNA1 with check table T005 (countries).

A value table is entered on the domain. It does not check anything by itself. It is only the proposal SAP offers when you create a foreign key on a field that uses this domain. The real check always comes from the foreign key.

Foreign key cardinality like 1:CN describes how many rows relate. Foreign key field type: key field, non-key field, or key field of a text table.

A text table holds language-dependent descriptions for a check table. It has the same key plus the language field SPRAS, and a foreign key of type "key fields of a text table". Example: T005 (countries) and its text table T005T (country names per language). Search helps and F4 lists show text from the text table automatically.

Say it in the interview: "The check table, defined through the foreign key at field level, is what actually validates input. The value table on the domain is only the default proposal for creating that foreign key."

2.10 Indexes

The primary index is created automatically from the key fields. A secondary index is created in SE11 (Goto → Indexes) on other fields that are often used in WHERE clauses. For example, an index on KNA1-NAME1 if users search customers by name. The database optimizer decides at runtime whether to use an index. You can check this in the ST05 explain plan.

Rules: put the most selective fields first, don't create many indexes (each slows INSERT and UPDATE), and avoid indexes on fields with few distinct values. On HANA, the column store usually makes secondary indexes unnecessary.

2.12 Search helps (F4 help)

A search help shows the user a list of possible values when they press F4 on a field.

Elementary search help: one selection method (a table or view), parameters, and dialog type (display immediately, or show a restriction popup first). Each parameter is marked IMP (import, taken from the screen into the help as a filter) and/or EXP (export, returned to the screen), with LPos/SPos for the position in the hit list and restriction popup.

Collective search help: groups several elementary helps as tabs. Example: DEBI for customers, with tabs to search by address, by sales area, and so on. You can add your own elementary help to a standard collective help with an append search help, which is a non-modifying enhancement.

Search help exit: a function module (copy F4IF_SHLP_EXIT_EXAMPLE) that changes the help at runtime, e.g. filters the list by the user's authorization. It is called at steps like SELONE, PRESEL, SELECT and DISP, controlled by callcontrol-step.

Attaching a search help, from strongest to weakest priority: on the screen field (dynpro), on the table field, on the data element, then via the check table or domain fixed values. In a report you can also use AT SELECTION-SCREEN ON VALUE-REQUEST FOR p_field and call F4IF_INT_TABLE_VALUE_REQUEST to show your own internal table as F4 help.

2.13 Lock objects

Lock objects protect data from being changed by two users at once (the full explanation is in module 12). In SE11 → Lock object → EZ_ORDER_LOG (the name must start with EZ or EY), you pick the primary table, the lock mode and the lock parameters (usually the key fields). Activating generates two function modules:

CALL FUNCTION 'ENQUEUE_EZ_ORDER_LOG'
  EXPORTING
    mode_zsd_order_log = 'E'
    vbeln              = lv_vbeln
  EXCEPTIONS
    foreign_lock       = 1        " someone else holds it
    system_failure     = 2
    OTHERS             = 3.
IF sy-subrc <> 0.
  MESSAGE ID sy-msgid TYPE 'E' NUMBER sy-msgno WITH sy-msgv1.  " "Order locked by user X"
ENDIF.
" ... change and save the data ...
CALL FUNCTION 'DEQUEUE_EZ_ORDER_LOG' EXPORTING vbeln = lv_vbeln.

Lock modes: E (exclusive, cumulative), X (exclusive, not cumulative), S (shared, read lock), O (optimistic, used in newer frameworks). Current locks are visible and deletable in SM12.

2.14 Table Maintenance Generator (TMG)

The TMG creates screens so users can maintain a Z table in SM30 without a program.

  1. In SE11 for the table: Utilities → Table Maintenance Generator (or transaction SE54).
  2. Enter an authorization group (e.g. &NC& for no restriction, or a custom group checked against object S_TABU_DIS).
  3. Enter a function group (e.g. ZFG_ORDER_LOG) where the screens will be generated.
  4. Choose one-step (one list screen where you edit everything) or two-step (overview list plus a detail screen per row), and let SAP propose screen numbers.
  5. Choose the recording routine: standard recording asks for a transport request on save, which you need for customizing tables.
  6. Create. Optionally create a parameter transaction in SE93 that calls SM30 with your table, so users get their own T-code.

TMG events (Environment → Modification → Events) let you add your own logic. The most used is event 01 (before saving), e.g. to fill "changed by" and "changed on" fields automatically. Event 05 runs when a new entry is created. You must regenerate the TMG after changing the table's fields.

2.15 Other DDIC topics interviewers touch

  • Type groups (TYPE-POOLS) hold global types and constants, e.g. ABAP with abap_true. Now replaced by interfaces or classes with constants.
  • Data change logging: tick "Log data changes" in technical settings, and profile parameter rec/client must be on. View changes in SCU3.
  • SE14 is the database utility: adjust and activate tables, and run conversions after structural changes.
  • SE16N / SE16 display table contents. SM30 maintains tables through the TMG.

Interview questions

Domain vs data element?

A domain is technical: type, length, value range. A data element is semantic: field labels, documentation and search help attachment. One domain can be reused by many data elements. For example, a domain CHAR10 can back both "Customer ID" and "Vendor ID".

Append structure vs include structure?

An append structure is assigned to exactly one table, always added at the end, and lets you add fields to SAP standard tables without a modification key. Appends survive upgrades. An include structure is an independent structure you can include in many tables or structures, anywhere in the field list. Custom fields in appends should start with ZZ or YY.

What are the types of views and when is each used?

A database view joins tables with an inner join and is read-only if it has more than one table. A projection view hides fields of a single table. A maintenance view lets users maintain related tables together in SM30. A help view uses an outer join and exists only to feed search helps. In S/4HANA, CDS views replace most new database view needs.

What is the value table vs check table?

A value table is set at domain level and is the default proposal for a check table. A check table is set at field level through a foreign key, and that is what actually enforces validation on screens. A value table alone does not validate anything.

What lock modes exist on a lock object?

E (exclusive, cumulative: the same user can lock again), X (exclusive, non-cumulative), S (shared, several users can read-lock) and O (optimistic, converted to E when changing). Locks are logical: they live in the enqueue server, not the database, and are visible in SM12.

When should you buffer a table, and when not?

Buffer small tables that are read often and changed rarely, such as customizing tables. Don't buffer tables that change frequently, large transaction tables, or tables where you always need the latest value. Note that SELECT ... BYPASSING BUFFER, aggregate functions, joins and ORDER BY on non-key fields skip the buffer.

How do you create a table with a maintenance screen?

Create domains and data elements, create the table in SE11 with delivery class C or A, set technical settings and activate. Then use Utilities → Table Maintenance Generator to choose an authorization group, function group and one-step or two-step screens. Users maintain it in SM30, or via a custom T-code created in SE93.

What is the difference between a structure and a table in SE11?

A table creates a physical database table that stores rows. A structure only describes a layout of fields and holds no data in the database. It is used for screens, interface parameters and program variables.

Why do CURR and QUAN fields need a reference field?

An amount means nothing without its currency (100 JPY vs 100 USD have different decimals), and a quantity means nothing without its unit. The reference field (CUKY or UNIT type) tells SAP how to format and convert the value on screens and in output. Activation fails if it is missing.

What is a conversion routine? Give an example.

A pair of function modules attached to a domain that convert between the screen format and the internal format. ALPHA pads numbers with leading zeros on input (CONVERSION_EXIT_ALPHA_INPUT) and removes them on output. If you select from KNA1 with '4711' instead of '0000004711', you find nothing. That's a classic bug.

What are TMG events? Which one have you used?

Hooks in generated maintenance screens where you add custom code. Event 01 (before save) is the most common, e.g. filling created-by and changed-on fields or validating entries. Event 05 (creating a new entry) can default values.

How do you add a field to a standard SAP table?

Create an append structure on the table with fields starting ZZ or YY, and activate it. Never modify the standard table directly. Check the table's enhancement category allows it. For screens and BAPIs you then also need the matching extension structures or exits.

Elementary vs collective search help?

Elementary has one selection method (table or view) with import and export parameters. Collective combines several elementary helps as tabs so users can search the same value in different ways. You extend a standard collective help with an append search help.

3.8 Field symbols and data references

A field symbol is a name that points to an existing piece of memory. It has no storage of its own. Think of it as a label you stick onto a variable or table row.

  <ls_order>-netwr = <ls_order>-netwr * '1.1'.     " changes the table row directly
ENDLOOP.

ENDLOOP.

UNASSIGN <lv_any>.

A data reference is a variable that stores the address of data. You can store it, pass it, put it in a table, and create new data at runtime.

DATA lr_data TYPE REF TO data.
CREATE DATA lr_data TYPE TABLE OF (lv_tabname).   " type known only at runtime
ASSIGN lr_data->* TO FIELD-SYMBOL(<lt_any>).       " dereference
SELECT * FROM (lv_tabname) INTO TABLE @<lt_any> UP TO 100 ROWS.

DATA(lr_num) = NEW i( 42 ).                       " anonymous data object
lr_num->* = lr_num->* + 1.
DATA(lr_row) = REF #( ls_order ).                 " reference to existing data

This combination (data reference plus field symbol plus dynamic table name) is the base of dynamic programming, used for generic tools such as a table download utility that works for any table.

Interview questions

What is a field symbol and why use it over a work area?

A field symbol is a placeholder that points to existing memory and has no memory of its own. In LOOP AT itab ASSIGNING <fs>, changes go straight into the table row, so no MODIFY is needed and no row is copied. That makes loops over large or wide tables faster. Always check IS ASSIGNED before use. Accessing an unassigned field symbol causes a dump.

Field symbol vs data reference?

A field symbol is an alias you assign to existing data. A data reference is a variable holding an address. You can pass references around, store them in tables and create anonymous data with NEW or CREATE DATA, then dereference with ->*. References are needed for dynamic programming, e.g. creating a table whose type is known only at runtime.

What happens if a table expression doesn't find a row?

itab[ key = val ] raises CX_SY_ITAB_LINE_NOT_FOUND. Avoid that by using VALUE #( itab[ ... ] OPTIONAL ) or DEFAULT, by checking line_exists( ) first, or by catching the exception in TRY/CATCH.

Explain sy-subrc, sy-tabix and sy-index.

sy-subrc is the return code of the last statement: 0 means success. sy-tabix is the current row index in internal table operations (LOOP, READ). sy-index is the loop counter in DO and WHILE loops.

What are REDUCE, FILTER and CORRESPONDING used for?

REDUCE folds a table into one value, such as a sum or concatenation. FILTER builds a new table with rows matching a condition and needs a sorted or hashed key on the filter field. CORRESPONDING moves same-named fields between structures or tables, with MAPPING for renamed fields and EXCEPT to skip fields.

What is the difference between TYPE and LIKE?

TYPE refers to a data type: built-in, DDIC or a local TYPES definition. LIKE refers to an existing data object, and the new variable takes the same type as that variable. In OO contexts, prefer TYPE.

What is the difference between CHECK and EXIT?

In a loop, CHECK cond skips the current pass if the condition is false (like CONTINUE), while EXIT leaves the loop completely. Outside loops both leave the current processing block, which is why they're discouraged outside loops: they hide the program flow.

What does MESSAGE TYPE 'E' do in START-OF-SELECTION vs AT SELECTION-SCREEN?

In AT SELECTION-SCREEN, the selection screen is shown again with the error, so the user can correct the input. In START-OF-SELECTION, the program ends and the user sees the message on an empty screen. To show an error and return to the selection screen from START-OF-SELECTION, use MESSAGE ... TYPE 'S' DISPLAY LIKE 'E' followed by LEAVE LIST-PROCESSING.

How do you create an internal table whose structure is known only at runtime?

Use a data reference: CREATE DATA lr_data TYPE STANDARD TABLE OF (lv_tabname), then ASSIGN lr_data->* TO <lt_any>. For a structure built from components at runtime, use RTTS: cl_abap_structdescr=>create( ) and cl_abap_tabledescr=>create( ).

What is the difference between c and string?

c has a fixed length, is filled with trailing spaces (which are ignored in most operations), and is used for DDIC fields. string has a dynamic length, keeps trailing spaces in backquote literals, and suits free text of any size. Literals: 'text' is type c (trailing spaces dropped), `text` is type string.

4.1 What an internal table is

An internal table is a table that lives in the program's memory while it runs. You read data from the database into it, process it there, and display or save it. It is the most-used data structure in ABAP. Each row has the same structure (the line type), and the table has a table kind and a key.

A work area is a structure with the same line type, used to hold one row at a time. Older code used OCCURS and header lines (a table and a work area with the same name). Header lines are obsolete and not allowed in classes. Never use them in new code.

TYPES: BEGIN OF ty_mat,
         matnr TYPE matnr,
         mtart TYPE mtart,
         brgew TYPE brgew,
       END OF ty_mat,
       tt_mat TYPE STANDARD TABLE OF ty_mat WITH EMPTY KEY.

DATA lt_mat TYPE tt_mat.         " internal table
DATA ls_mat TYPE ty_mat.         " work area

APPEND ls_mat TO lt_mat.                       " add at end (standard / sorted if order kept)

4.4 Reading one row

READ TABLE lt_mat INTO ls_mat INDEX 1.
READ TABLE lt_mat INTO ls_mat WITH KEY matnr = 'M1'.               " linear on standard

READ TABLE lt_mat TRANSPORTING NO FIELDS WITH KEY matnr = 'M1'.    " only check existence
READ TABLE lt_sorted INTO DATA(ls_s) WITH TABLE KEY vbeln = 'V1' posnr = '10'.  " full table key

SORT lt_mat BY matnr.
READ TABLE lt_mat INTO ls_mat WITH KEY matnr = 'M1' BINARY SEARCH. " fast, needs SORT by same fields
IF sy-subrc = 0.   " found; sy-tabix = row number
ENDIF.

" Modern equivalents

Common mistake: using BINARY SEARCH when the table is not sorted by exactly those fields, in that order. The read silently returns "not found" for rows that exist. SORT first, by the same fields, ascending.

After a failed BINARY SEARCH, sy-subrc is 4 and sy-tabix points to where the row would be inserted (or 8 if past the end). The parallel cursor technique uses this.

4.5 Looping

LOOP AT lt_mat INTO ls_mat.                     " copy each row into a work area
ENDLOOP.
LOOP AT lt_mat ASSIGNING FIELD-SYMBOL(<ls>) WHERE mtart = 'FERT'.   " no copy, can change
  <ls>-brgew = <ls>-brgew * 2.
ENDLOOP.
LOOP AT lt_mat REFERENCE INTO DATA(lr).        " data reference to each row
ENDLOOP.
LOOP AT lt_mat INTO ls_mat FROM 5 TO 10.        " index range
ENDLOOP.

INTO vs ASSIGNING: INTO copies every row into the work area. Changing it needs MODIFY lt_mat FROM ls_mat. ASSIGNING points at the row itself, so changes are direct and nothing is copied. It is faster for wide rows and large tables, and is the recommended default.

LOOP WHERE on a sorted table with a condition on the leading key fields is optimised by SAP (binary search to the first row). On a standard table, LOOP WHERE always scans every row.

4.6 Control-level processing (AT NEW, AT END OF)

Used to print subtotals per group in classic code. The table must be sorted by the group fields, and the group field must be on the left of the structure, because AT NEW compares all fields to the left too.

SORT lt_orders BY kunnr vbeln.
LOOP AT lt_orders INTO DATA(ls_o).
  AT FIRST.            WRITE / 'Orders by customer'.  ENDAT.
  AT NEW kunnr.        WRITE / ls_o-kunnr.             ENDAT.
  WRITE: /5 ls_o-vbeln, ls_o-netwr.
  AT END OF kunnr.     SUM. WRITE: /5 'Subtotal', ls_o-netwr.  ENDAT.
  AT LAST.             SUM. WRITE: / 'Grand total', ls_o-netwr. ENDAT.
ENDLOOP.

Inside AT ... ENDAT, fields to the right of the group field show * (char fields) or are initial. Use a copy of the row from before the AT if you need them. SUM adds up all numeric fields of the group. In modern code, LOOP AT ... GROUP BY replaces this.

4.7 Changing and deleting

MODIFY lt_mat FROM ls_mat INDEX 3.
MODIFY lt_mat FROM ls_mat TRANSPORTING brgew WHERE mtart = 'FERT'.   " mass update one field
MODIFY TABLE lt_hash FROM ls_kna1.                                  " by table key
lt_mat[ matnr = 'M1' ]-brgew = 10.                                  " modern

DELETE lt_mat INDEX 2.
DELETE lt_mat WHERE mtart = 'HALB'.
DELETE TABLE lt_hash WITH TABLE KEY kunnr = '1000'.
SORT lt_mat BY matnr.
DELETE ADJACENT DUPLICATES FROM lt_mat COMPARING matnr.
CLEAR lt_mat.      " remove all rows, keep memory
FREE lt_mat.       " remove all rows and release memory

Don't DELETE rows from the table you are looping over with INTO (it shifts indexes). Collect the indexes or use DELETE WHERE after the loop.

4.8 SORT, size and comparisons

SORT lt_mat BY mtart ASCENDING brgew DESCENDING.
SORT lt_mat STABLE BY mtart.           " keeps the relative order of equal rows
DATA(lv_n) = lines( lt_mat ).           " DESCRIBE TABLE lt_mat LINES lv_n. (old)
IF lt_mat IS INITIAL. ENDIF.            " empty?
IF lt_a = lt_b. ENDIF.                  " compares row by row

A sorted table can't be sorted with SORT (it is always in key order, and the statement gives a syntax error). Standard and hashed tables can be sorted.

4.9 Secondary keys

DATA lt_kna1 TYPE SORTED TABLE OF kna1
     WITH UNIQUE KEY kunnr
     WITH NON-UNIQUE SORTED KEY by_land COMPONENTS land1.

LOOP AT lt_kna1 INTO DATA(ls_k) USING KEY by_land WHERE land1 = 'IN'.
ENDLOOP.
READ TABLE lt_kna1 INTO ls_k WITH KEY by_land COMPONENTS land1 = 'DE'.
DATA(ls_k2) = lt_kna1[ KEY by_land land1 = 'DE' ].

Secondary keys give fast access by a second set of fields without keeping two tables. Hashed secondary keys must be unique. They use extra memory and are rebuilt lazily after changes, so use them for tables that are filled once and read many times.

4.10 Nested loops and the parallel cursor

The classic performance problem: for every header, loop over all items.

" SLOW: 10,000 headers x 100,000 items = 1 billion comparisons
LOOP AT lt_vbak INTO DATA(h).
  LOOP AT lt_vbap INTO DATA(i) WHERE vbeln = h-vbeln.   " scans all items each time
  ENDLOOP.
ENDLOOP.

" FAST option 1: make the item table sorted by vbeln
DATA lt_items TYPE SORTED TABLE OF vbap WITH NON-UNIQUE KEY vbeln.
LOOP AT lt_vbak INTO h.
  LOOP AT lt_items INTO i WHERE vbeln = h-vbeln.         " binary search to first match
  ENDLOOP.
ENDLOOP.

" FAST option 2: parallel cursor on standard tables
SORT: lt_vbak BY vbeln, lt_vbap BY vbeln.
LOOP AT lt_vbak ASSIGNING FIELD-SYMBOL(<h>).
  READ TABLE lt_vbap TRANSPORTING NO FIELDS WITH KEY vbeln = <h>-vbeln BINARY SEARCH.
  CHECK sy-subrc = 0.
  DATA(lv_idx) = sy-tabix.
  LOOP AT lt_vbap ASSIGNING FIELD-SYMBOL(<i>) FROM lv_idx.
    IF <i>-vbeln <> <h>-vbeln. EXIT. ENDIF.
    " process item
  ENDLOOP.
ENDLOOP.
Say it in the interview: "For nested loops I either declare the inner table as a sorted table on the join field, so LOOP WHERE uses binary search, or I use the parallel cursor technique with SORT, READ BINARY SEARCH and LOOP FROM index with EXIT when the key changes."

4.11 Ranges and select-options

A range table has four fields: SIGN (I include, E exclude), OPTION (EQ, NE, BT between, NB, CP pattern, GT, LT, GE, LE), LOW and HIGH. SELECT-OPTIONS on a selection screen creates one automatically. You can also build your own and use them with IN in SQL and IF.

DATA lr_mtart TYPE RANGE OF mtart.
lr_mtart = VALUE #( sign = 'I' option = 'EQ' ( low = 'FERT' ) ( low = 'HALB' ) ).
SELECT matnr FROM mara WHERE mtart IN @lr_mtart INTO TABLE @DATA(lt_m).
IF lv_mtart IN lr_mtart. ENDIF.
Remember: an empty range in a WHERE clause means "no restriction", so all rows are returned, the same trap as FOR ALL ENTRIES with an empty driver table. Also, very large ranges (thousands of entries) can exceed the database statement size limit and dump.

Interview questions

Standard vs sorted vs hashed table: which would you choose and why?

Hashed for big lookup tables read by full unique key, because access time stays constant. Sorted when you need ordered data or read by a leading part of the key, at logarithmic cost. Standard when you mostly append and loop, or need index access. If you must read a standard table by key, SORT it once and use BINARY SEARCH.

APPEND vs INSERT vs COLLECT vs MODIFY?

APPEND adds at the end (standard tables). INSERT adds by key or index and keeps sort order in sorted tables. COLLECT adds a row, or sums the numeric fields if a row with the same non-numeric key already exists. MODIFY changes an existing row by index or key.

What is the parallel cursor technique?

When looping over header and item tables, a nested LOOP ... WHERE on a standard table scans the item table once per header. Parallel cursor sorts both tables, finds the first matching item with BINARY SEARCH, loops from that index and exits when the key changes. Cost drops from roughly n×m to n log m. A sorted item table with LOOP ... WHERE on the key gives a similar gain with cleaner code.

What are secondary keys on internal tables?

Extra sorted or hashed keys declared with WITH ... KEY name COMPONENTS .... They let you read a table quickly by fields other than the primary key, e.g. READ TABLE lt WITH KEY by_kunnr COMPONENTS kunnr = x. They cost memory and are updated lazily.

How do you delete duplicates from an internal table?

SORT by the comparison fields, then DELETE ADJACENT DUPLICATES FROM itab COMPARING f1 f2. Without the sort, only neighbouring duplicates are removed.

What is the difference between CLEAR, REFRESH and FREE?

CLEAR itab deletes all rows but keeps the initial memory. REFRESH does the same for the table body and is obsolete (and on a table with a header line, CLEAR clears only the header). FREE deletes all rows and releases the memory, which is useful for very large tables you no longer need.

What is COLLECT used for, and what is required?

Building totals: COLLECT adds a row, or if a row with the same values in all non-numeric fields (the key) already exists, adds the numeric fields to it. All non-key fields must be numeric (i, p, f). It works best on hashed or sorted tables. On standard tables SAP builds an internal hash, which breaks if you also use APPEND.

Why does READ TABLE ... BINARY SEARCH sometimes not find an existing row?

Because the table isn't sorted by exactly the search fields in the same order, or was changed after sorting. Binary search assumes order, and with the wrong order it jumps past the row. Always SORT by the same fields right before, or use a sorted table.

Which table type for a lookup of 500,000 customers by KUNNR?

A hashed table with unique key KUNNR. Each lookup takes constant time regardless of size. If you also need ranges or the first-n-fields of a key, a sorted table is the alternative.

Basics

5.1 Open SQL vs Native SQL

Open SQL (called ABAP SQL in newer releases) is SQL written directly in ABAP. It works on DDIC tables and views, is checked by the syntax checker, adds the client automatically, can use the table buffer, and works on any database SAP supports. Native SQL (EXEC SQL ... ENDEXEC or ADBC classes like CL_SQL_STATEMENT) sends database-specific SQL directly, bypasses the client handling and buffer, and isn't portable. Use it only in rare, justified cases. On HANA, use AMDP instead (module 16).

5.2 SELECT basics

" One row by full primary key
SELECT SINGLE matnr, mtart, meins FROM mara
  WHERE matnr = @lv_matnr
  INTO @DATA(ls_mara).
IF sy-subrc <> 0.  " 4 = not found
ENDIF.

" Many rows into an internal table
SELECT matnr, mtart FROM mara
  WHERE mtart IN @s_mtart
    AND ersda >= @lv_from
  ORDER BY matnr
  INTO TABLE @DATA(lt_mara)
  UP TO 500 ROWS.

" Into an existing structure with fields of the same names
SELECT kunnr, name1, ort01 FROM kna1
  WHERE land1 = 'IN'
  INTO CORRESPONDING FIELDS OF TABLE @lt_cust.

" Row by row (SELECT loop) - avoid for large data, each pass is a fetch
SELECT matnr FROM mara WHERE mtart = 'FERT' INTO @DATA(lv_matnr2).
ENDSELECT.

Strict modern syntax: fields separated by commas, every ABAP variable escaped with @, and the INTO clause can come at the end. Once you use one modern element in a statement, the whole statement must be modern.

After a SELECT: sy-subrc = 0 if at least one row was read, 4 if none. sy-dbcnt = number of rows read.

5.3 WHERE clause options

WHERE erdat BETWEEN @lv_from AND @lv_to
  AND kunnr IN @s_kunnr               " select-option or range
  AND name1 LIKE 'SAN%'               " % any characters, _ one character
  AND auart IN ('ZOR', 'ZRE')
  AND lifsk = @space                  " empty field
  AND faksk IS NULL                   " only for fields that can be NULL, e.g. from outer joins
  AND NOT vbtyp = 'C'
  AND vbeln IN ( SELECT vbeln FROM vbap WHERE matnr = @lv_matnr )   " subquery

To use an index, the WHERE clause should contain the leading fields of the index with = or IN. NOT, <> and LIKE '%x' (leading wildcard) usually can't use an index.

5.4 Joins

" INNER JOIN: only headers that have items
SELECT k~vbeln, k~kunnr, p~posnr, p~matnr, p~kwmeng
  FROM vbak AS k
  INNER JOIN vbap AS p ON p~vbeln = k~vbeln
  WHERE k~erdat IN @s_erdat
  INTO TABLE @DATA(lt_items).

" LEFT OUTER JOIN: all customers, with orders if any
SELECT c~kunnr, c~name1, k~vbeln
  FROM kna1 AS c
  LEFT OUTER JOIN vbak AS k ON k~kunnr = c~kunnr
  WHERE c~land1 = 'IN'
  INTO TABLE @DATA(lt_cust_orders).

" Three tables
SELECT k~vbeln, p~matnr, t~maktx
  FROM vbak AS k
  INNER JOIN vbap AS p ON p~vbeln = k~vbeln
  LEFT OUTER JOIN makt AS t ON t~matnr = p~matnr AND t~spras = @sy-langu
  WHERE k~vkorg = @p_vkorg
  INTO TABLE @DATA(lt_all).

Inner join returns only rows that have a match in both tables. Left outer join returns all rows from the left table, with NULLs (initial values in ABAP) where there is no match on the right. Old releases had restrictions on WHERE conditions on the right table of outer joins, and these are lifted in newer releases. Right outer join and cross join are also available in newer releases.

Common mistake: forgetting a key field in the ON condition, e.g. joining MAKT without spras. That multiplies rows (one per language). Always join on the full key of the right-hand table.

5.5 FOR ALL ENTRIES (FAE) in depth

FAE reads database rows that match entries in an internal table (the driver table). SAP splits the driver table into packets and sends several SELECTs (or one with IN lists, depending on the database), then merges the results and removes duplicate rows.

IF lt_items IS NOT INITIAL.                               " rule 1
  DATA(lt_drv) = lt_items.
  SORT lt_drv BY matnr.
  DELETE ADJACENT DUPLICATES FROM lt_drv COMPARING matnr. " rule 2: fewer DB calls

  SELECT matnr, werks, ekgrp FROM marc                    " rule 3: select all key fields
    FOR ALL ENTRIES IN @lt_drv
    WHERE matnr = @lt_drv-matnr
      AND werks = @p_werks
    INTO TABLE @DATA(lt_marc).
ENDIF.
  1. Empty driver table: the whole WHERE clause is ignored and the entire table is read. This is the most famous ABAP bug. Always check IS NOT INITIAL.
  2. Duplicates in the driver cause extra database work. Sort and delete duplicates first.
  3. Result duplicates are removed: if you don't select enough fields to make rows unique, real rows disappear. Select the full primary key.
  4. Not allowed together with: aggregate functions (SUM COUNT...), ORDER BY (except PRIMARY KEY in newer releases), GROUP BY and HAVING. Sort the result in ABAP instead.
  5. The driver table fields must be type-compatible with the database fields. Comparing different lengths can give wrong results or errors.
  6. You can use only = conditions (and some others) with driver fields. LIKE and BETWEEN with driver fields aren't allowed.
Say it in the interview: "Before FOR ALL ENTRIES I always check the driver table is not initial, I remove duplicates from it, and I select all key fields so the automatic duplicate removal doesn't drop rows. On HANA I prefer a join or a CDS view if possible."

5.6 Aggregates and grouping

SELECT kunnr, COUNT(*) AS cnt, SUM( netwr ) AS total, MAX( erdat ) AS last_order
  FROM vbak
  WHERE erdat IN @s_erdat
  GROUP BY kunnr
  HAVING SUM( netwr ) > 100000
  ORDER BY total DESCENDING
  INTO TABLE @DATA(lt_tot).

SELECT COUNT(*) FROM vbak WHERE kunnr = @lv_kunnr INTO @DATA(lv_cnt).
SELECT DISTINCT kunnr FROM vbak INTO TABLE @DATA(lt_unique).

Every non-aggregated field in the field list must be in GROUP BY. HAVING filters groups after aggregation, while WHERE filters rows before. Aggregates bypass the table buffer.

5.7 SQL expressions (7.40 SP08 onwards)

SELECT vbeln,
       netwr,
       netwr * 2 AS double_value,
       CASE WHEN netwr > 100000 THEN 'HIGH' ELSE 'NORMAL' END AS prio,
       CAST( kwmeng AS INT4 ) AS qty,
       concat( vkorg, vtweg ) AS sales_area,
       coalesce( lifsk, 'NONE' ) AS block,
       @sy-datum AS run_date,
       'X' AS flag
  FROM vbak
  INTO TABLE @DATA(lt_x).

Other functions: substring, length, upper, lower, lpad, rtrim, replace, abs, ceil, floor, round, div, mod, date functions such as dats_days_between and dats_add_days. This is code pushdown in its simplest form: the calculation happens in the database.

Also available: UNION / UNION ALL, common table expressions with WITH, SELECT FROM @itab (selecting from an internal table, from 7.52), and window functions in newer releases.

5.8 Writing data

INSERT zsd_order_log FROM @ls_log.              " sy-subrc 4 if the key already exists
INSERT zsd_order_log FROM TABLE @lt_log ACCEPTING DUPLICATE KEYS.
UPDATE zsd_order_log FROM @ls_log.              " by primary key; 4 if not found
UPDATE zsd_order_log SET status = 'C', aedat = @sy-datum WHERE vbeln = @lv_vbeln.
MODIFY zsd_order_log FROM @ls_log.              " insert if new, update if exists
DELETE FROM zsd_order_log WHERE erdat < @lv_old.
DELETE zsd_order_log FROM @ls_log.              " by key
COMMIT WORK.
Rule: never write directly to SAP standard tables (VBAK, MARA, BSEG...) with INSERT, UPDATE or DELETE. That bypasses all business logic, change documents and dependent tables, and can corrupt data. Always use a BAPI, standard function module or transaction. Direct DML is only for your own Z tables.

5.9 Large data volumes: PACKAGE SIZE and cursors

SELECT vbeln, posnr, matnr FROM vbap
  WHERE erdat IN @s_erdat
  INTO TABLE @DATA(lt_pack) PACKAGE SIZE 10000.
  " process 10,000 rows, then the next 10,000 overwrite them
ENDSELECT.

OPEN CURSOR WITH HOLD @DATA(lv_cur) FOR SELECT vbeln FROM vbak WHERE erdat IN @s_erdat.
DO.
  FETCH NEXT CURSOR @lv_cur INTO TABLE @DATA(lt_chunk) PACKAGE SIZE 5000.
  IF sy-subrc <> 0. EXIT. ENDIF.
ENDDO.
CLOSE CURSOR @lv_cur.

This keeps memory low when reading millions of rows. Don't COMMIT inside a SELECT loop without WITH HOLD, because the commit closes the cursor and dumps.

5.10 Authorization checks with SQL

Open SQL does not check authorizations automatically. A custom report must call AUTHORITY-CHECK itself, e.g. that the user may display a sales organisation:

AUTHORITY-CHECK OBJECT 'V_VBAK_VKO'
  ID 'VKORG' FIELD p_vkorg
  ID 'ACTVT' FIELD '03'.           " 03 = display, 01 = create, 02 = change
IF sy-subrc <> 0.
  MESSAGE e000(zsd_msg) WITH p_vkorg.   " No authorization for sales org &1
ENDIF.

CDS views with DCL access control are the exception: there, authorization is applied automatically when read via Open SQL (module 16). Use SU53 to see a user's last failed authorization check, and SU24/PFCG for roles.

Interview questions

What are the rules and pitfalls of FOR ALL ENTRIES?
  • If the driver table is empty, the WHERE clause is ignored and every row is read. Always check IS NOT INITIAL first.
  • Duplicates are removed from the result, so select all key fields you need, or you may lose rows.
  • Sort and delete duplicates in the driver table first to reduce database calls.
  • Aggregates and ORDER BY aren't allowed in the same statement.
JOIN or FOR ALL ENTRIES: which is better?

A join is usually better, especially on HANA, because the database does the work in one round trip. FOR ALL ENTRIES is useful when the second table is a pooled or cluster table in older systems, when data comes from a non-database source such as an uploaded file, or when a join would be very complex. Don't join more than a handful of tables, and make sure join fields are indexed.

SELECT SINGLE vs SELECT UP TO 1 ROWS?

Use SELECT SINGLE when you supply the full primary key, so exactly one row is expected and it can use the table buffer. Use UP TO 1 ROWS when you have only part of the key or need the first row by an ORDER BY.

Why avoid SELECT *?

It transfers every column, which wastes network and memory. On HANA, a column store, it also forces reading every column. Select only the fields you need, into a matching structure.

Why avoid SELECT inside LOOP?

Each pass is a separate database round trip, so 10,000 rows means 10,000 calls. Read all needed data once with a join or FOR ALL ENTRIES into an internal table, then read from memory inside the loop (ideally a hashed or sorted table).

What is a secondary index and when do you create one?

An extra database index on non-key fields, created in SE11, used when a frequent selection filters on fields not in the primary key. Too many indexes slow down inserts and updates. On HANA, the column store makes secondary indexes rarely necessary.

What is the difference between INTO TABLE and APPENDING TABLE?

INTO TABLE clears the internal table first, then fills it. APPENDING TABLE keeps existing rows and adds the new ones at the end.

What is the difference between WHERE and HAVING?

WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY and aggregation, so it can use aggregates like SUM( netwr ) > 1000.

INSERT vs MODIFY on a database table?

INSERT adds a new row and fails (sy-subrc 4, or a dump for FROM TABLE without ACCEPTING DUPLICATE KEYS) if the key exists. MODIFY inserts the row if the key doesn't exist and updates it if it does.

Does Open SQL check authorizations?

No. You must code AUTHORITY-CHECK for the relevant authorization object yourself. Only CDS views with access control (DCL) apply row-level authorization automatically when read through ABAP SQL.

How do you read millions of rows without running out of memory?

Use PACKAGE SIZE in a SELECT loop, or OPEN CURSOR / FETCH with PACKAGE SIZE, and process each packet before reading the next. Select only needed fields, and run in background.

Modularization

Basics

6.1 Why modularize

Modularization means splitting code into reusable, named units. It makes programs readable, avoids copy-paste, lets you test parts separately, and allows other programs to reuse logic. ABAP has several techniques, and you should know where each one fits:

TechniqueScopeStatus
Include programsSource-code splitting only, no own logic boundaryUsed to organise big programs

6.2 Include programs

An include (type I) is a piece of source code inserted with INCLUDE zinc_top.. It can't run alone and has no parameters. A common report structure is Z_REPORT with includes Z_REPORT_TOP (global data), Z_REPORT_SEL (selection screen), Z_REPORT_F01 (forms or local classes). Module pools generated in SE80 use the same pattern (TOP, O01 for PBO modules, I01 for PAI, F01 for forms).

6.3 Subroutines (FORM / PERFORM)

PERFORM calc_total USING lv_price lv_qty CHANGING lv_total.

FORM calc_total USING    iv_price TYPE p
                         VALUE(iv_qty) TYPE i     " by value
                CHANGING cv_total TYPE p.
  cv_total = iv_price * iv_qty.
ENDFORM.

USING without VALUE is by reference (changes would affect the caller, even though it reads as input). CHANGING by reference changes the caller's variable directly. CHANGING VALUE( ) is "by value and result": it works on a copy and writes back only when the form ends normally. TABLES passes internal tables and is obsolete. You can call a form in another program with PERFORM form IN PROGRAM zprog, a technique often seen in SAP user exits and forms.

6.4 Function modules

Function modules (FMs) are global procedures created in SE37. Each belongs to a function group (created in SE80 or SE37 → Goto → Function groups), which is a program of type F containing:

  • the TOP include (LZFG_ORDERTOP): global data shared by all FMs in the group, kept in memory between calls in the same session,
  • the UXX include listing each FM's include (LZFG_ORDERU01...),
  • optional screens, PBO/PAI modules, and forms.

FM interface tabs:

  • Import: input parameters, optional or with defaults.
  • Export: output parameters.
  • Changing: in and out.
  • Tables: obsolete for new FMs, still in many BAPIs.
  • Exceptions: classic exceptions raised with RAISE not_found. or MESSAGE ... RAISING not_found, mapped to sy-subrc by the caller. You can also tick "Exception classes" and use class-based exceptions.
  • Source code.
FUNCTION z_get_customer_name.
*"  IMPORTING   VALUE(iv_kunnr) TYPE kunnr
*"  EXPORTING   VALUE(ev_name)  TYPE name1_gp
*"  EXCEPTIONS  not_found
  SELECT SINGLE name1 FROM kna1 WHERE kunnr = @iv_kunnr INTO @ev_name.
  IF sy-subrc <> 0.
    RAISE not_found.
  ENDIF.
ENDFUNCTION.

" Caller
CALL FUNCTION 'Z_GET_CUSTOMER_NAME'
  EXPORTING  iv_kunnr  = lv_kunnr
  IMPORTING  ev_name   = lv_name
  EXCEPTIONS not_found = 1
             OTHERS    = 2.
CASE sy-subrc.
  WHEN 1. MESSAGE 'Customer not found' TYPE 'S' DISPLAY LIKE 'E'.
ENDCASE.

Note the direction flip: what the FM imports, the caller exports. If the caller doesn't list an exception and the FM raises it, the program dumps (RAISE_EXCEPTION). That's why OTHERS is always added.

Processing types (Attributes tab)

  • Normal function module: called locally.
  • Remote-enabled module (RFC): can be called from other systems. All parameters must be pass by value and typed with DDIC types (no generic types). BAPIs are RFC FMs.
  • Update module: called IN UPDATE TASK and executed by the update work process at COMMIT WORK. Start options: immediate (V1), immediate not restartable, delayed (V2), collective run. Update modules have only importing and tables parameters (no exporting), because they run later and asynchronously. See module 12.

6.5 Pass by value vs pass by reference

By reference: the formal parameter is just another name for the caller's variable. Fast, with no copy. For importing parameters of methods, the system prevents changing it. By value: a copy is made at the call. Changes affect only the copy (for exporting/changing, the result is copied back at the end). That is slower for big tables, but required for RFC and update FMs, and for RETURNING parameters of methods.

Say it in the interview: "I pass by reference for large tables to avoid copying, and by value where the interface requires it: RFC and update modules, and RETURNING parameters. For FMs I always handle the classic exceptions including OTHERS, or I use class-based exceptions."

6.6 Finding and testing function modules

  • SE37 → F4 on the name with wildcards, e.g. *CUSTOMER*NAME*. Or SE80 → repository info system, or SE84.
  • Test any FM in SE37 with F8: enter parameter values, execute, and see the results and runtime. You can save test data as test data directories.
  • Where-used list (Ctrl+Shift+F3) shows which programs call it.
  • Commonly used standard FMs: CONVERSION_EXIT_ALPHA_INPUT/OUTPUT, READ_TEXT, POPUP_TO_CONFIRM, GUI_UPLOAD/GUI_DOWNLOAD, REUSE_ALV_GRID_DISPLAY, BAPI_TRANSACTION_COMMIT, SO_NEW_DOCUMENT_ATT_SEND_API1 (old mail; use CL_BCS now), DATE_GET_WEEK, RP_CALC_DATE_IN_INTERVAL, NUMBER_GET_NEXT (number ranges, SNRO), JOB_OPEN/JOB_SUBMIT/JOB_CLOSE.

6.7 Other ways to call programs

SUBMIT zreport WITH p_vkorg = '1000' WITH s_erdat IN lr_dates AND RETURN.   " run another report
SUBMIT zreport VIA JOB lv_jobname NUMBER lv_jobcount AND RETURN.          " schedule as job
CALL TRANSACTION 'VA03' AND SKIP FIRST SCREEN.     " after SET PARAMETER ID 'AUN' FIELD lv_vbeln
LEAVE TO TRANSACTION 'VA01'.                       " no return

Memory for passing data: SET/GET PARAMETER ID (SAP memory, user-wide, single fields, survives across sessions of the user), EXPORT ... TO MEMORY ID / IMPORT ... FROM MEMORY ID (ABAP memory, within one call chain, any data), and shared memory or shared objects for cross-user caching.

Interview favourite: SAP memory vs ABAP memory. SAP memory (SET/GET PARAMETER) is global for the user's logon and holds small field values like the last sales order number. ABAP memory (EXPORT/IMPORT TO MEMORY) lives in one internal session chain, e.g. between a program and the program it SUBMITs with AND RETURN, and can hold whole internal tables.

Interview questions

Subroutine vs function module vs method?

A subroutine is local to its program and obsolete for new development. A function module is global, lives in a function group (which shares global data), can be RFC-enabled or an update module, and supports exceptions. Methods belong to classes and support encapsulation, inheritance and class-based exceptions. New code should use methods. Function modules are still needed for RFC, BAPIs and update tasks.

Pass by value vs pass by reference?

By reference (the default for IMPORTING in methods) passes the address, so it is fast and no copy is made. For EXPORTING or CHANGING it changes the caller's data directly. By value (VALUE( )) works on a copy, which is safer but slower for large tables. RFC function modules must pass by value.

What is a function group and why does it matter?

A container for related function modules that share global data, screens and includes (the TOP include). Calling one FM loads the whole group into memory, and global data persists between calls within the same session. That can be useful, or cause surprising bugs.

Why must RFC function modules pass parameters by value?

The caller and the function run in different systems or sessions with separate memory, so there is no shared address to reference. Data is serialised, sent over the network and copied. That is why RFC FMs also need DDIC types for all parameters.

SAP memory vs ABAP memory?

SAP memory is user-specific and global across all sessions of the logon, accessed with SET/GET PARAMETER ID, for small values such as a document number. ABAP memory is local to one external session's call chain, accessed with EXPORT/IMPORT ... MEMORY ID, and can hold complex data like internal tables.

What happens if an FM raises an exception the caller didn't handle?

For classic exceptions, if the caller has no EXCEPTIONS addition for it (and no OTHERS), the program terminates with a runtime error. If the caller lists it, sy-subrc is set to the assigned number. For class-based exceptions, it propagates until a TRY/CATCH handles it, or dumps.

What is the global data of a function group, and what is the risk?

Data declared in the TOP include is shared by all FMs in the group and stays in memory for the whole internal session. It's useful for buffering, e.g. caching results. The risk is that leftover values from a previous call affect the next call. Clear or reinitialise such data properly, often through an explicit "refresh" FM.

7.7 Dialog programming (module pool) basics

A module pool (type M) is a program made of screens, used for custom transactions with several screens. Create it in SE80, add screens in the Screen Painter (SE51), menus and buttons in the Menu Painter (SE41), and a T-code in SE93.

Each screen has flow logic with two events:

PROCESS BEFORE OUTPUT.          " PBO: before the screen is shown
  MODULE status_0100.
PROCESS AFTER INPUT.            " PAI: after the user presses a key
  MODULE exit_0100 AT EXIT-COMMAND.      " function type E buttons skip field checks
  CHAIN.
    FIELD: zorder-kunnr, zorder-vkorg.
    MODULE validate_customer ON CHAIN-REQUEST.   " on error, all fields in the CHAIN stay editable
  ENDCHAIN.
  FIELD zorder-matnr MODULE check_material ON REQUEST.
  MODULE user_command_0100.
PROCESS ON VALUE-REQUEST.       " POV: custom F4
  FIELD zorder-kunnr MODULE f4_customer.
PROCESS ON HELP-REQUEST.        " POH: custom F1

Screen fields with the same name as program variables are transported automatically: program to screen at the end of PBO, screen to program at the start of PAI. The OK code field (type OK in the element list) receives sy-ucomm. CALL SCREEN 200 calls a screen (stacked, return with LEAVE TO SCREEN 0), SET SCREEN 200 sets the next screen, and LEAVE TO SCREEN 200 goes there immediately.

Other screen elements: subscreens (CALL SUBSCREEN), tabstrips, and table controls (CONTROLS tc TYPE TABLEVIEW USING SCREEN 100, with LOOP AT itab WITH CONTROL tc in both PBO and PAI).

7.8 Running reports in the background

  • From the selection screen: Program → Execute in Background (F9), or schedule in SM36 with a variant. Monitor in SM37.
  • Check sy-batch to skip GUI-only logic (popups, GUI_DOWNLOAD) when running in a job.
  • Output goes to the spool (SP01). For files, write to the application server with OPEN DATASET.
  • From code: JOB_OPEN, SUBMIT ... VIA JOB ... AND RETURN, JOB_CLOSE with start immediately.

Interview questions

List the events of a classical report in order.

LOAD-OF-PROGRAM, INITIALIZATION (set defaults), AT SELECTION-SCREEN OUTPUT (change screen before display, e.g. hide fields), AT SELECTION-SCREEN (validate input; also ON field, ON VALUE-REQUEST for F4, ON HELP-REQUEST for F1), START-OF-SELECTION (main logic), END-OF-SELECTION (output). TOP-OF-PAGE and END-OF-PAGE fire during list output.

How do you validate selection screen input?

In AT SELECTION-SCREEN ON p_field (or ON BLOCK), check the value against the database and issue MESSAGE ... TYPE 'E'. The screen returns with the field ready for input. Validating in START-OF-SELECTION would end the program instead.

How many secondary lists can an interactive report have?

20 secondary lists plus the basic list (sy-lsind 0 to 20). Going beyond that causes a runtime error.

CL_SALV_TABLE vs CL_GUI_ALV_GRID?

CL_SALV_TABLE is quick: no screen or field catalog needed, and good for display-only reports. CL_GUI_ALV_GRID needs a screen, a custom container and a field catalog, but supports editable cells, data change events and full toolbar control. Choose GUI_ALV_GRID when users must edit data in the grid.

How do you make an ALV editable and save changes?

With CL_GUI_ALV_GRID, set edit = abap_true in the field catalog for the columns, register edit events (register_edit_event with mc_evt_modified or mc_evt_enter), handle DATA_CHANGED to validate, and on SAVE call check_changed_data( ) to transfer changes to the internal table before updating the database.

How do you dynamically hide a selection-screen field?

Give fields a MODIF ID, then in AT SELECTION-SCREEN OUTPUT loop at SCREEN, check screen-group1, set screen-active = 0 (or invisible = 1), and MODIFY SCREEN. Usually this is triggered by a radio button with USER-COMMAND.

What is the difference between AT SELECTION-SCREEN OUTPUT and INITIALIZATION?

INITIALIZATION runs once before the first display of the selection screen and is used for default values. AT SELECTION-SCREEN OUTPUT runs before every display of the selection screen, including after each Enter or radio-button click, and is used to change screen attributes dynamically.

What is HIDE in interactive reports?

HIDE stores the current values of the named fields together with the list line just written. When the user clicks that line, AT LINE-SELECTION gets those fields restored automatically, so you know which record was selected.

What is CHAIN ... ENDCHAIN in a screen's PAI?

It groups several fields for a validation module. If the module raises an error message, all fields in the chain stay ready for input (not only the one in error), so the user can correct any of them together.

What does AT EXIT-COMMAND do?

A module with AT EXIT-COMMAND runs before any field checks, but only for buttons with function type E (like Back, Exit and Cancel). It lets the user leave a screen even if required fields are empty or contain errors.

How do you add a custom button to an ALV toolbar?

For CL_GUI_ALV_GRID, handle the TOOLBAR event and append to e_object->mt_toolbar, then handle USER_COMMAND for its function code. For CL_SALV_TABLE in full screen, copy the GUI status SALV_STANDARD into your program, add the button, set it with set_screen_status, and handle the ADDED_FUNCTION event.

How do you colour a cell or row in ALV?

For a row, add a 4-character field to the output table, fill it with a colour code like 'C610' (C + colour 6 + intensified 1 + inverse 0), and set info_fname in the layout. For cells, add a field of type LVC_T_SCOL, fill it with field name and colour per cell, and set ctab_fname in the layout.

8.1 Why OOP in ABAP

Object-oriented ABAP (ABAP Objects) organises code into classes that bundle data (attributes) and behaviour (methods). The four pillars are:

  • Encapsulation: hide internal data and expose only what's needed through public methods.
  • Inheritance: a subclass reuses and extends a superclass.
  • Polymorphism: the same call behaves differently depending on the actual object.
  • Abstraction: work with interfaces and abstract classes instead of concrete details.

In practice, OOP gives testable code (ABAP Unit), reusable logic, cleaner exception handling, and it is mandatory for modern frameworks: ALV OO, BAdIs, RAP, workflow classes, OData DPC classes. Also, many newer language features only work in classes, where obsolete statements like header lines and TABLES parameters are forbidden.

8.2 Class definition and implementation

CLASS lcl_order DEFINITION.
  PUBLIC SECTION.
    TYPES ty_status TYPE c LENGTH 1.
    CONSTANTS c_open TYPE ty_status VALUE 'O'.
    DATA mv_id TYPE vbeln_va READ-ONLY.            " visible outside, but only readable
    CLASS-DATA gv_count TYPE i.                    " static: shared by all instances

    METHODS constructor IMPORTING iv_id TYPE vbeln_va.
    METHODS get_value   RETURNING VALUE(rv_value) TYPE netwr_ak.
    METHODS set_status  IMPORTING iv_status TYPE ty_status
                        RAISING   zcx_order_error.
    CLASS-METHODS create IMPORTING iv_id TYPE vbeln_va
                         RETURNING VALUE(ro_order) TYPE REF TO lcl_order.
  PROTECTED SECTION.
    DATA mv_status TYPE ty_status.                 " visible in subclasses
  PRIVATE SECTION.
    DATA mt_items TYPE STANDARD TABLE OF vbap WITH EMPTY KEY.   " only inside this class
    METHODS load_items.
ENDCLASS.

CLASS lcl_order IMPLEMENTATION.
  METHOD constructor.
    mv_id = iv_id.
    mv_status = c_open.
    gv_count += 1.
    load_items( ).
  ENDMETHOD.
  METHOD create.
    ro_order = NEW #( iv_id ).
  ENDMETHOD.
  METHOD get_value.
    rv_value = REDUCE #( INIT s = 0 FOR i IN mt_items NEXT s = s + i-netwr ).
  ENDMETHOD.
  METHOD set_status.
    IF iv_status NA 'OCX'.
      RAISE EXCEPTION NEW zcx_order_error( textid = zcx_order_error=>invalid_status ).
    ENDIF.
    mv_status = iv_status.
  ENDMETHOD.
  METHOD load_items.
    SELECT * FROM vbap WHERE vbeln = @mv_id INTO TABLE @mt_items.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(lo_order) = NEW lcl_order( '0000012345' ).     " or CREATE OBJECT lo_order EXPORTING iv_id = ...
  WRITE: / lo_order->mv_id, lo_order->get_value( ), lcl_order=>gv_count.

Syntax to remember: -> for instance components, => for static components and constants, me-> for the current object, super-> for the superclass method.

Local classes are defined inside one program and used only there. Global classes are created in SE24 or ADT (names start with ZCL_), are reusable system-wide, and can be tested with F8 in SE24.

8.3 Visibility and instance vs static

SectionVisible to
PUBLICEveryone
PROTECTEDThe class itself and its subclasses
PRIVATEOnly the class itself (and its friends)

Instance attributes (DATA) exist once per object. Static attributes (CLASS-DATA) exist once per class for the whole internal session, shared by all objects. Static methods (CLASS-METHODS) can be called without an object, but can only access static attributes. READ-ONLY makes a public attribute readable but not changeable from outside.

Friends: CLASS lcl_a DEFINITION FRIENDS lcl_test. gives lcl_test access to private and protected components. It is used mainly for unit test classes.

Instantiation control: CREATE PUBLIC (default), CREATE PROTECTED (only the class and subclasses can create objects), CREATE PRIVATE (only the class itself, used for singletons and factories).

8.4 Method parameters

  • IMPORTING: input. By reference by default and can't be changed in the method. OPTIONAL or DEFAULT make it optional. Check with IS SUPPLIED.
  • EXPORTING: output, can be several.
  • CHANGING: in and out.
  • RETURNING VALUE( ): exactly one, always by value. Makes a functional method usable in expressions: IF lo_order->get_value( ) > 1000.
  • RAISING: class-based exceptions the method can raise. EXCEPTIONS (classic) is also possible but can't be mixed with RAISING in one method.

Call styles: lo->m( iv_a = 1 ), lo->m( 1 ) if there is only one importing parameter, lo->m( EXPORTING iv_a = 1 IMPORTING ev_b = lv_b ), or the old CALL METHOD lo->m EXPORTING ....

8.5 Constructors

Instance constructor (METHODS constructor): runs automatically on NEW or CREATE OBJECT. It may have only IMPORTING parameters (and exceptions), and must be public, or the class's instantiation must match. In a subclass, the constructor must call super->constructor( ) before accessing instance components.

Static constructor (CLASS-METHODS class_constructor): runs once per internal session, automatically, before the first access to the class (first object, or first static access). No parameters. Used to load static configuration, e.g. read a Z customizing table into a static table.

Order when creating a subclass object for the first time: superclass static constructor → subclass static constructor → subclass instance constructor, which calls the superclass instance constructor.

8.6 Inheritance

CLASS lcl_vehicle DEFINITION ABSTRACT.
  PUBLIC SECTION.
    METHODS constructor IMPORTING iv_wheels TYPE i.
    METHODS describe RETURNING VALUE(rv) TYPE string.
    METHODS max_speed ABSTRACT RETURNING VALUE(rv) TYPE i.   " no implementation here
  PROTECTED SECTION.
    DATA mv_wheels TYPE i.
ENDCLASS.
CLASS lcl_vehicle IMPLEMENTATION.
  METHOD constructor. mv_wheels = iv_wheels. ENDMETHOD.
  METHOD describe.    rv = |{ mv_wheels } wheels, max { max_speed( ) } km/h|. ENDMETHOD.
ENDCLASS.

CLASS lcl_car DEFINITION INHERITING FROM lcl_vehicle FINAL.
  PUBLIC SECTION.
    METHODS constructor.
    METHODS max_speed REDEFINITION.
    METHODS describe  REDEFINITION.
ENDCLASS.
CLASS lcl_car IMPLEMENTATION.
  METHOD constructor. super->constructor( iv_wheels = 4 ). ENDMETHOD.
  METHOD max_speed.   rv = 180. ENDMETHOD.
  METHOD describe.    rv = |Car: { super->describe( ) }|. ENDMETHOD.   " extend the parent
ENDCLASS.
  • ABAP supports single inheritance only: one superclass. Multiple behaviours come from interfaces.
  • REDEFINITION overrides a method. The signature can't change. Static methods and constructors can't be redefined (constructors are re-declared instead).
  • ABSTRACT class: can't be instantiated. ABSTRACT method: no implementation, so subclasses must implement it.
  • FINAL class: can't be inherited. FINAL method: can't be redefined.
  • Private components of the superclass are inherited but not accessible in the subclass. Protected ones are.
  • All classes ultimately inherit from OBJECT.

8.7 Interfaces

INTERFACE lif_output.
  METHODS send IMPORTING iv_text TYPE string RETURNING VALUE(rv_ok) TYPE abap_bool.
ENDINTERFACE.

CLASS lcl_email DEFINITION.
  PUBLIC SECTION.
    INTERFACES lif_output.
    ALIASES send FOR lif_output~send.        " shorter name
ENDCLASS.
CLASS lcl_email IMPLEMENTATION.
  METHOD lif_output~send. rv_ok = abap_true. ENDMETHOD.
ENDCLASS.

CLASS lcl_printer DEFINITION.
  PUBLIC SECTION. INTERFACES lif_output.
ENDCLASS.
CLASS lcl_printer IMPLEMENTATION.
  METHOD lif_output~send. rv_ok = abap_true. ENDMETHOD.

" Polymorphism: the caller only knows the interface
DATA lt_channels TYPE STANDARD TABLE OF REF TO lif_output WITH EMPTY KEY.
lt_channels = VALUE #( ( NEW lcl_email( ) ) ( NEW lcl_printer( ) ) ).
LOOP AT lt_channels INTO DATA(lo_ch).
  lo_ch->send( `Invoice 4711` ).         " email or print, decided at runtime
ENDLOOP.

An interface contains only declarations. All its components are public. A class can implement many interfaces. Interface components are accessed as interface~component. Interfaces can include other interfaces. Since 7.40 interface methods can be marked DEFAULT IGNORE or DEFAULT FAIL, so implementing classes don't have to implement every method. Important SAP interfaces: IF_WORKFLOW, IF_AMDP_MARKER_HDB, IF_OO_ADT_CLASSRUN (run a class in ADT console with out->write( )), IF_SERIALIZABLE_OBJECT, BAdI interfaces like IF_EX_ME_PROCESS_PO_CUST.

8.8 Casting

Up-cast (SAP calls it narrowing): assign a subclass or implementing-class reference to a superclass or interface reference. Always safe, uses =. You lose access to subclass-only components through that reference.

Down-cast (SAP calls it widening): assign a general reference back to a specific type. Needs ?= or CAST. It is checked at runtime and raises CX_SY_MOVE_CAST_ERROR if the object isn't of that type. Check first with IS INSTANCE OF.

DATA lo_v TYPE REF TO lcl_vehicle.
lo_v = NEW lcl_car( ).                    " up-cast
IF lo_v IS INSTANCE OF lcl_car.
  DATA(lo_c) = CAST lcl_car( lo_v ).      " down-cast
ENDIF.
CASE TYPE OF lo_v.
  WHEN TYPE lcl_car INTO DATA(lo_car). ...
ENDCASE.

Static type is the type of the reference variable (decides which components you can access). Dynamic type is the class of the actual object (decides which implementation runs).

The raiser doesn't know who listens, which keeps classes loosely coupled. Every handler gets the implicit parameter sender. Static events (CLASS-EVENTS) are registered without FOR. SET HANDLER ... ACTIVATION abap_false deregisters.

8.10 Class-based exceptions

Exception classes inherit from one of three abstract classes under CX_ROOT:

SuperclassDeclaration in RAISINGCheckedUse for
CX_STATIC_CHECKRequired (or handle inside)Compiler warns at syntax checkExpected business errors the caller must handle: "order not found"
CX_DYNAMIC_CHECKRequired if it can leave the methodOnly at runtimeErrors the caller can prevent: division by zero, invalid index
CX_NO_CHECKNot allowed (always implicit)NeverErrors that can happen anywhere: out of resources

Create a custom exception class in SE24 or ADT, e.g. ZCX_ORDER_ERROR inheriting from CX_STATIC_CHECK, with message texts. Either use the "With message class" option, implementing IF_T100_MESSAGE (texts from SE91 with attributes as &1 to &4 placeholders), or use OTR texts.

TRY.
    lo_order->set_status( 'Z' ).
  CATCH zcx_order_error INTO DATA(lx).
    MESSAGE lx TYPE 'E'.                          " exception objects with T100 texts can be sent directly
  CATCH cx_root INTO DATA(lx_any).                 " catch-all, use sparingly
    DATA(lv_text) = lx_any->get_text( ).
    DATA(lx_prev) = lx_any->previous.             " chained exception
  CLEANUP.
    " release resources if the exception leaves this block
ENDTRY.

" Re-raise with context
CATCH cx_sy_open_sql_db INTO DATA(lx_db).
  RAISE EXCEPTION NEW zcx_order_error( previous = lx_db ).

RETRY in a CATCH block restarts the TRY block (e.g. after fixing input). RAISE RESUMABLE EXCEPTION together with CATCH BEFORE UNWIND and RESUME lets the program continue after the RAISE statement. Exceptions travel up the call stack until a CATCH handles them, and if none does, a dump UNCAUGHT_EXCEPTION occurs.

Interview questions

Abstract class vs interface?

An abstract class can have implemented methods, attributes and constructors, and a class can inherit from only one. An interface has only declarations (plus constants and attributes), and a class can implement many. Use an abstract class for shared base behaviour in an "is-a" hierarchy. Use an interface for a contract that unrelated classes fulfil, e.g. IF_WORKFLOW.

Instance constructor vs static constructor?

The instance CONSTRUCTOR runs on every NEW or CREATE OBJECT, can have importing parameters only, and initialises instance attributes. The CLASS_CONSTRUCTOR runs once per session, before the first access to the class, has no parameters, and initialises static data.

Explain the three exception class types.

CX_STATIC_CHECK: must be handled or declared in RAISING, and the compiler checks this. CX_DYNAMIC_CHECK: must be declared, checked only at runtime, used for errors the caller can avoid (e.g. CX_SY_ZERODIVIDE). CX_NO_CHECK: cannot be declared, used for errors that can occur anywhere, such as resource shortages.

What is polymorphism? Give an ABAP example.

The same method call behaves differently depending on the object's real class. Example: an interface zif_output with method send, implemented by zcl_email_output and zcl_print_output. The caller holds a REF TO zif_output and calls send( ) without knowing which one it has.

Narrowing vs widening cast?

Up-cast (narrowing in SAP terms): assigning a subclass reference to a superclass reference. Always allowed, using =. Down-cast (widening): assigning a superclass reference to a subclass reference. Needs ?= or CAST #( ) and raises CX_SY_MOVE_CAST_ERROR if the object isn't really that subclass.

Can a final method be redefined? Can an abstract class be instantiated?

No to both. A final method can't be redefined in subclasses, and a final class can't be inherited. An abstract class can't be instantiated directly, only its concrete subclasses.

How do events work in ABAP Objects?

A class declares EVENTS evt EXPORTING ... and fires it with RAISE EVENT. Another class defines a handler method FOR EVENT evt OF class and registers it at runtime with SET HANDLER obj->handler FOR sender. The ALV grid's double-click is the classic example.

What is the difference between a static and an instance method?

An instance method belongs to an object, is called with ->, and can use both instance and static attributes. A static method belongs to the class, is called with => without creating an object, and can use only static attributes. Static methods can't be redefined.

What is a functional method?

A method with a RETURNING parameter. It can be used directly in expressions, conditions and as an operand: IF lo->is_valid( ) = abap_true or lv_x = lo->get_value( ) * 2. RETURNING is always pass by value, and a method can have only one.

Can a class inherit from two classes in ABAP?

No, ABAP has single inheritance. A class can implement any number of interfaces to combine several contracts.

What is the purpose of the FRIENDS addition?

It lets a named class (or interface) access the private and protected components of the granting class. It is mostly used to give an ABAP Unit test class access to internals. Friendship isn't inherited in the reverse direction and isn't transitive.

What is the difference between CATCH and CLEANUP?

CATCH handles the exception and processing continues after ENDTRY. CLEANUP runs only when an exception is not caught in this TRY block and is about to leave it. It is used to restore a consistent state before the exception moves up the call stack.

Why use exception classes instead of classic EXCEPTIONS?

Class-based exceptions carry information (texts, attributes, previous exceptions), propagate automatically through call levels without manual sy-subrc checks, can be grouped through inheritance, and support CLEANUP and RETRY. Classic exceptions are just a return code.

Forms: SAPscript, Smart Forms, Adobe Forms

Core

9.1 What forms are and how printing works

Forms are formatted business documents: invoices, purchase orders, delivery notes, payslips, labels and certificates. SAP has three form technologies (SAPscript, Smart Forms and Adobe Forms). Every one of them follows the same pattern:

Business document saved (e.g. billing doc in VF01) │ output determination: condition technique finds output type (e.g. RD00) for this doc ▼ Output record in NAST (or in S/4: output request via BRF+ / SAP Output Management) │ dispatch time: immediately, with job RSNAST00, or manually ▼ Driver (print) program ── reads document data (VBRK, VBRP, KNA1...) ── calls the form ▼ Form layout ── spool request (SP01) ── printer, PDF, email or fax

The driver program holds the data logic. The form holds the layout and only small display logic. Keeping data reading in the driver is a best practice interviewers like to hear.

9.2 Output determination with NACE

NACE is the central transaction for classic output control:

  1. Choose the application: V1 sales, V2 shipping, V3 billing, EF purchasing, ME purchasing documents, and so on.
  2. Output types: e.g. BA00 (order confirmation), LD00 (delivery note), RD00 (invoice), NEU (purchase order). Copy the standard one to a Z type, e.g. ZRD0.
  3. In the output type's Processing routines: medium (1 print, 5 external send/email, 6 EDI, 8 special function), the program (your driver), the form routine (the FORM called, typically ENTRY), and the form name (Smart Form, SAPscript or PDF form).
  4. Condition records (VV11 for sales, VV21 for shipping, VV31 for billing, MN04 for purchase orders) decide when the output is proposed, e.g. for this sales org and customer, print to printer LP01 immediately.

In the document (VA02, VF02 → Extras → Output) you can see, repeat or print the output. The processing log shows errors from the driver program.

In S/4HANA, many documents (billing, purchase orders, sales orders) can use the newer SAP S/4HANA Output Management, based on BRF+ determination and Adobe forms (often via the Fiori app "Maintain Form Templates"), instead of NACE. Projects may use either, so ask which is active.

9.3 SAPscript

The oldest technology (SE71). It is client-dependent and text-based. You still meet it in old standard forms like the original purchase order MEDRUCK.

  • Header: basic settings and administrative data, plus the first page.
  • Pages: each page names its next page, e.g. FIRST → NEXT → NEXT.
  • Windows: MAIN (the body that flows across pages; up to 99 main windows per page), VAR (variable content), CONST (constant).
  • Page windows: position and size of each window on each page.
  • Paragraph formats and character formats, or a style from SE72.
  • Text elements in windows: /E ITEM_LINE, called by name from the driver.
CALL FUNCTION 'OPEN_FORM'   EXPORTING form = 'ZSD_INVOICE' language = sy-langu device = 'PRINTER'.
CALL FUNCTION 'START_FORM'  EXPORTING form = 'ZSD_INVOICE'.     " optional, for several forms in one spool
LOOP AT gt_items INTO gs_item.
  CALL FUNCTION 'WRITE_FORM' EXPORTING element = 'ITEM_LINE' window = 'MAIN'.
ENDLOOP.
CALL FUNCTION 'WRITE_FORM'  EXPORTING element = 'TOTAL' window = 'MAIN'.
CALL FUNCTION 'END_FORM'.
CALL FUNCTION 'CLOSE_FORM'.

In the form, program variables appear as &GS_ITEM-MATNR&. Control commands start with /: in the tag column, e.g. /: IF &GS_ITEM-NETWR& GT 0, /: INCLUDE ZTEXT OBJECT TEXT ID ST (standard text), /: PERFORM get_text IN PROGRAM zsd_sub USING ... CHANGING ... (call ABAP from the form), /: PROTECT ... ENDPROTECT (no page break inside), /: NEW-PAGE. Debug SAPscript by activating the form debugger in SE71 (Utilities → Activate debugger), or with program RSTXDBUG.

Transport: because SAPscript is client-dependent, you copy forms between clients with SCC1 or the SE71 copy function, and text tools RSTXSCRP import/export.

9.4 Smart Forms

Created in transaction SMARTFORMS. They are client-independent, have a graphical form builder, and on activation SAP generates a function module that contains all the logic.

Structure of a Smart Form

  • Global settings
    • Form attributes: language, style, page format.
    • Form interface: the parameters the driver passes (importing, exporting, tables, exceptions). This becomes the generated FM's interface.
    • Global definitions: global data, types, field symbols, initialization (code that runs once at the start, e.g. read extra data), and form routines (FORMs used inside the form).
  • Pages and windows
    • Main window: only one per form, but it appears on every page. Its content flows across pages automatically.
    • Secondary windows: fixed content like logo, address and header data, shown on the page they're placed on.
    • Copies window: shows text depending on original or copy ("ORIGINAL" / "COPY").
    • Final window: processed at the end, after everything else. Used for values known only at the end, e.g. total number of pages on page 1.
  • Nodes inside windows: text (with &field& variables), graphic (logo uploaded in SE78), address node (formats addresses by country rules from ADRC), table (with header, main area and footer, line types and cell borders), template (fixed grid of cells, for header boxes), loop, alternative (IF/ELSE), program lines (ABAP code; input and output parameters must be declared), command (new page, page counter reset), folder (grouping) and include text (standard texts from SO10).

Styles (SMARTSTYLES) define paragraph and character formats, fonts and tab stops, reusable across forms.

Common Smart Form tasks

  • Page X of Y: use system fields &SFSY-PAGE& and &SFSY-FORMPAGES&. Others: SFSY-DATE, SFSY-TIME, SFSY-JOBPAGES.
  • Totals: in the table node's Calculations tab (sum of a field into a total variable), or with program lines.
  • Page break after each customer: a command node with "Go to new page" in a loop, triggered on change.
  • Logo: upload a BMP in SE78, then add a graphic node.
  • Barcodes: define the barcode in SE73 (or new barcode technology), and assign it to a character format in the style.
  • Translation: SE63. Texts in the form can be translated without copying it.
  • Migration: a SAPscript form can be migrated to a Smart Form in the SMARTFORMS transaction (Utilities → Migrate SAPscript form).

9.5 Adobe Forms (Interactive Forms by Adobe)

Created in transaction SFP. This is SAP's strategic form technology, required for many S/4HANA output scenarios and Fiori. It needs Adobe Document Services (ADS), a Java-based rendering service (on-premise on a Java stack, or the cloud service on BTP) connected via destination ADS.

An Adobe form has two parts:

Interview questions

Why call SSF_FUNCTION_MODULE_NAME instead of the generated FM directly?

The generated function module name (/1BCDWB/SF00000xxx) can differ between systems because it is generated on activation in each system. Looking it up by form name at runtime keeps the driver program working after transport.

SAPscript vs Smart Forms?

Smart Forms are client-independent, have a graphical editor, support only one main window but have tables and loops built in, and generate a function module, so no OPEN_FORM/WRITE_FORM calls are needed. SAPscript is client-dependent, text-based and needs explicit driver calls. Smart Forms can also be output as XML or HTML.

How do you debug a Smart Form?

Put a BREAK-POINT in a program-lines node, or set a breakpoint in the generated FM (find it via Environment → Function module name). You can also debug the driver program into the generated FM call.

What is the final window in Smart Forms?

A window processed last, after all other windows, even though it appears earlier on the page. Use it for values known only at the end, such as "Page X of Y" totals or grand totals printed on the first page.

How do you attach a custom form to a standard output like a sales order?

In NACE, pick the application (V1 for sales), choose the output type, and under Processing routines assign the custom driver program, form routine and Smart Form or Adobe form name. Usually you copy the standard output type and driver program first.

How do you print "Page 1 of 5" in a Smart Form?

In a text node in a secondary window, write Page &SFSY-PAGE& of &SFSY-FORMPAGES&. If the total shows wrong values or *, check the field's output length, e.g. &SFSY-FORMPAGES(3ZC)& to condense and remove leading zeros.

How do you send a Smart Form as a PDF email?

Call the generated FM with control_parameters-getotf = 'X' and no dialog, take job_output_info-otfdata, convert with CONVERT_OTF to PDF, convert the binary to solix with cl_bcs_convert, then build the mail with CL_BCS (document, attachment, recipient), call send and COMMIT WORK. Check SOST for the status.

What is the difference between a template and a table in Smart Forms?

A template has a fixed number of rows and columns defined at design time, used for fixed layouts like an address and header box. A table is dynamic: it loops over an internal table, so the number of rows depends on the data, and it can break across pages with header and footer repeated.

What is ADS and why is it required?

Adobe Document Services render the Adobe form layout plus data into a PDF. ABAP prepares the data and calls ADS over HTTP via the ADS destination. Without a working ADS connection, Adobe forms can't produce output.

How do you change a standard SAP form without modifying it?

Copy the standard form (and, if needed, the driver program) into the customer namespace, change the copy, and assign the copy to the output type in NACE (or in output management). Never change the original SAP form.

10.1 Why enhancements exist

Standard SAP rarely matches every business rule. You have three options to change its behaviour:

  1. Customizing (SPRO): configuration, no code. Always the first choice.
  2. Enhancement: add custom code at places SAP prepared or allows. Upgrade-safe.
  3. Modification: change SAP's own code. Needs an access key from SAP (SSCR), must be re-checked in every upgrade (SPAU/SPDD), and is avoided wherever possible.

The enhancement techniques, from oldest to newest: user exits, customer exits, classic BAdIs, the enhancement framework (implicit and explicit enhancement points and sections, plus kernel BAdIs), and in S/4HANA Cloud the "key user" and "developer" extensibility based on released BAdIs.

10.2 User exits

Empty subroutines (FORMs) that SAP put into special includes of standard programs, mainly in SD. Because the includes belong to SAP, changing them technically counts as a modification (an object key is requested the first time), but SAP intends them to be changed and they aren't overwritten in upgrades.

  • Sales order (program SAPMV45A), include MV45AFZZ: USEREXIT_SAVE_DOCUMENT_PREPARE (last checks before save), USEREXIT_SAVE_DOCUMENT (save extra data), USEREXIT_MOVE_FIELD_TO_VBAK / ..._VBAP (fill header or item fields), USEREXIT_FIELD_MODIFICATION (screen field attributes). Include MV45AFZB has more item-level exits.
  • Pricing: RV61AFZA/RV61AFZB, and condition value formulas in VOFM.
  • Delivery: MV50AFZ1. Billing: RV60AFZZ, and copy-control routines in VOFM.

Find them by searching for "USEREXIT" in the program (SE38 → find), or in SPRO → Sales and Distribution → System Modifications → User Exits.

10.3 Customer exits (SMOD / CMOD)

SAP-defined hooks grouped in an enhancement (seen in SMOD, e.g. MEREQ001 for purchase requisitions, V45A0002, MM06E005). You activate them through your own project in CMOD.

Types:

  • Function exits: SAP calls CALL CUSTOMER-FUNCTION '001', which runs function module EXIT_SAPLxxxx_001. Inside it is an include ZXxxxU01 where you write code. The FM interface tells you what data you get and may change.
  • Screen exits: a subscreen area on an SAP screen, so you can add your own subscreen with custom fields (e.g. extra fields on the PO header).
  • Menu exits: menu entries starting with + (e.g. +CU1) that you can activate and give a text.
  • Table exits: CI_ includes in SAP tables.
  1. Find the enhancement: SMOD with F4 by package or keyword, or search the program for CALL CUSTOMER-FUNCTION.
  2. CMOD → create project ZMM_PR → Enhancement assignments → enter MEREQ001. Each enhancement can be assigned to only one project.
  3. Components → double-click the function exit → double-click the ZX... include → create it and write code.
  4. Activate the project. Exits do nothing until the project is active.

10.4 Classic BAdIs (SE18 / SE19)

A Business Add-In is an object-oriented hook: SAP defines an interface (the BAdI definition), and you write a class that implements it (the BAdI implementation). SAP code calls the interface methods at defined points.

" How SAP calls a classic BAdI (inside standard code)
DATA lo_badi TYPE REF TO if_ex_badi_name.
CALL METHOD cl_exithandler=>get_instance
  CHANGING instance = lo_badi.
CALL METHOD lo_badi->method_name EXPORTING ... CHANGING ...

Properties set in the definition:

  • Multiple use: several active implementations allowed, all are called. Single use allows only one active implementation.
  • Filter-dependent: implementations are tied to filter values (e.g. country), and only the implementation for the current filter runs.
  • Within the implementation you code the interface methods in the generated class ZCL_IM_....

10.5 Enhancement framework (from NetWeaver 7.0)

The enhancement framework unified all new enhancement types under enhancement spots (containers) and enhancement implementations.

Implicit enhancement points

These exist automatically, without SAP defining them, at: the start and end of every function module, FORM, method and include; the end of structures (to add fields to non-DDIC structures); at the end of the public, protected and private sections of classes; and as pre-, post- and overwrite-exits for class methods. In SE80/SE38: Edit → Enhancement Operations → Show Implicit Enhancement Options (or the spiral icon), right-click the yellow line → Create Implementation. Implicit enhancements are powerful but risky: you can change data anywhere, so use them only when no BAdI or exit fits, and document them well.

Explicit enhancement points and sections

SAP places them deliberately in code: ENHANCEMENT-POINT name SPOTS spot. (add code there) and ENHANCEMENT-SECTION name SPOTS spot. ... END-ENHANCEMENT-SECTION. (your implementation replaces the SAP code inside the section; only one active implementation).

New (kernel) BAdIs

Defined in an enhancement spot (SE18 → enhancement spot), implemented in SE19 (create an enhancement implementation, then a BAdI implementation with your class). They are called with dedicated ABAP statements and handled by the kernel, so they're much faster than classic BAdIs:

DATA lo_badi TYPE REF TO badi_sd_sales_item.          " BAdI name as the type
GET BADI lo_badi FILTERS vkorg = lv_vkorg.           " filter values if any
CALL BADI lo_badi->check_item EXPORTING is_item = ls_item CHANGING ct_messages = lt_msg.

Extra features: fallback class (default implementation used when no customer implementation is active), filter values with complex conditions, context for stateful BAdIs, sorting of multiple implementations (BAdI BADI_SORTER / layer), and switch framework integration.

10.6 Finding the right enhancement: a practical procedure

  1. Ask the functional consultant and check the SPRO documentation for the process. Many BAdIs are listed under "Business Add-Ins" nodes in SPRO.
  2. Classic BAdIs: put a breakpoint in method GET_INSTANCE of class CL_EXITHANDLER, run the transaction, and note exit_name each time it stops.
  3. New BAdIs: in the debugger, Breakpoints → Breakpoint at → Statement → GET BADI (or CALL BADI).
  4. SQL trace: in ST05, trace while running the transaction and look for reads on SXS_ATTR, SXS_INTER (classic BAdIs) or BADI_IMPL / ENHSPOTOBJ-related tables. Read V_EXT_IMP and V_EXT_ACT for classic BAdIs.
  5. Customer exits: search the main program for CALL CUSTOMER-FUNCTION, get the package of the transaction (SE93 → package), then SMOD → F4 → information system → package.
  6. Implicit points: when nothing else exists, at the start or end of a suitable FM, form or method found by debugging.
  7. Check the BAdI documentation in SE18 and existing implementations before creating a new one (for single-use BAdIs, one may already be active).

10.9 Best practices

  • Prefer, in order: customizing → BAdI or exit → explicit enhancement → implicit enhancement → modification.
  • Keep enhancement code small: call a method of your own global class, so logic is testable and reusable.
  • Always restrict by organisational unit (company code, sales org, document type), because the enhancement runs for everyone.
  • Never COMMIT WORK, and don't call screens or popups inside BAdIs or exits unless documented. Save-time exits run inside SAP's LUW.
  • Use a switch or a Z customizing table to turn the logic on and off without a transport.
  • After upgrades, check enhancements in SPAU_ENH.
Say it in the interview: "First I check if customizing can solve it. If not, I look for a BAdI, using the CL_EXITHANDLER breakpoint for classic and the GET BADI statement breakpoint for kernel BAdIs, or a customer exit through SMOD. Implicit enhancements are my last resort before a modification. Inside the enhancement I keep the code thin and call a global class."

Interview questions

How do you find a BADI for a transaction?
  • Set a breakpoint in CL_EXITHANDLER=>GET_INSTANCE (classic BADIs), run the transaction and note the exit names.
  • For new BADIs, use a breakpoint on the GET BADI statement, or the debugger's statement breakpoint.
  • Run an SQL trace in ST05 on tables SXS_ATTR / BADI_IMPL.
  • Search the program's package in SE84 or SE18, or read SAP notes and SPRO documentation.
Classic BADI vs kernel BADI?

Classic BADIs are instantiated through CL_EXITHANDLER, which is slower, and live outside enhancement spots. Kernel BADIs are integrated into the ABAP kernel (GET BADI/CALL BADI), belong to enhancement spots, support filter values, fallback classes and context, and perform better.

What is a multiple-use BADI and a filter-dependent BADI?

Multiple-use: several active implementations all run, with no guaranteed order unless sorting is defined. Single-use: only one active implementation. Filter-dependent: implementations are tied to filter values (e.g. country or company code), so only the matching implementation runs.

User exit vs customer exit vs BADI?

User exits are FORM routines in SAP code. Editing them is a modification, mostly in SD. Customer exits are predefined hooks managed via CMOD that don't need modification, but each is usable in one project only. BADIs are object-oriented, can have multiple implementations and filters, and are the preferred approach today.

Enhancement point vs enhancement section?

An enhancement point lets you add code at that place, and the original code still runs. An enhancement section replaces the code inside the section with your implementation. Only one active implementation of a section is allowed.

How do you add a custom field to a standard screen, e.g. a sales order?

Add the field to the table through an append structure (e.g. VBAK via ZAVBAK). Then add it to the screen using the screen exit SAP provides: for sales orders, subscreen 8309 or 8459 in SAPMV45A with modification registration, or a BADI or customer exit screen area elsewhere. Fill and save it through the user exits.

What is a fallback class in a new BAdI?

A default implementation defined with the BAdI. It runs when no customer implementation is active, or when none matches the filter. It is used for single-use BAdIs so there is always defined behaviour.

Can a customer exit be used in two CMOD projects?

No. An SAP enhancement (SMOD) can be assigned to only one CMOD project. If it's already used, add your code to the existing project.

What are BTEs?

Business Transaction Events, an FI enhancement technique managed in FIBF. SAP calls interface function modules at events (Publish & Subscribe or Process interfaces). You copy the sample FM, add logic, and register it for the event in a product or customer entry.

What happens to enhancements during an upgrade?

BAdI implementations, customer exits and enhancement implementations stay, because they live in customer objects. Implicit enhancements and modifications may need adjustment if SAP changed the surrounding code, and you check them in SPAU_ENH and SPAU. That's why BAdIs are preferred.

11.1 What a conversion is

A conversion (the C in RICEFW) loads data from a legacy system into SAP, usually before go-live: customers, vendors, materials, open sales orders, open POs, balances. The typical flow is Extract (from legacy), Transform (map fields and values, clean data), Load (into SAP via a BAPI, BDC or migration tool), and Validate (reconcile counts and amounts). Interview questions

Call transaction vs session method?

Call transaction is immediate and faster, supports synchronous or asynchronous update, and returns messages that you must log yourself. Session method creates a batch input session processed later in SM35, always updates synchronously, writes a log automatically and is better for large volumes and error reprocessing.

Why prefer a BAPI over BDC?

BDC replays screens, so it breaks when screens or field positions change (or in Fiori-only processes), and it is slower. A BAPI is a stable, released API that returns structured messages in a RETURN table and is upgrade-safe. Use BDC only when no BAPI exists.

How do you handle table controls in BDC?

Fields are indexed by row, e.g. RV45A-MABNR(01), (02). You also handle page-down (=P+) when rows exceed the visible lines, and set a default screen size via CTU_PARAMS-DEFSIZE = 'X' so the number of visible rows is the same everywhere.

How would you upload a file from the application server in background?

GUI_UPLOAD doesn't work in background jobs because there is no SAP GUI. Use OPEN DATASET lv_file FOR INPUT IN TEXT MODE ENCODING DEFAULT, READ DATASET in a loop, then CLOSE DATASET. Check sy-subrc after each step.

What is BDC_OKCODE and BDC_CURSOR?

Special FNAM values in BDCDATA. BDC_OKCODE holds the function code to trigger on that screen, such as /00 for Enter, =UPDA or =BU for Save, or /11. BDC_CURSOR places the cursor on a field, which some screens need before an action like F4 or a double-click.

Why might a BDC work in foreground (mode A) but fail in background (mode N)?

Different screen size changes the number of table-control rows (fix with defsize), screens or popups that appear only in some situations (warnings, dialogs), user parameters or defaults that differ, or GUI-dependent controls like ALV grids and text editors that can't be processed by batch input. Recording carefully and using a BAPI instead avoids most of these.

What is the X-structure in BAPIs?

A parallel structure with the same field names but type BAPIUPDATE (CHAR 1). Setting a field to 'X' tells the BAPI that this field should be updated. It distinguishes "set to blank" from "leave unchanged", and is mainly used in change BAPIs.

How do you pass custom fields into a BAPI?

Through the EXTENSIONIN table (type BAPIPAREX): fill STRUCTURE with the extension structure name (e.g. BAPE_VBAK) and VALUEPART1 to 4 with the field values in the structure's layout. The custom fields must exist in the append of the database table and in the BAPI extension structures (e.g. BAPE_VBAK, BAPE_VBAKX, VBAKKOZ, VBAKKOZX for sales orders).

LUW, locks and update techniques

Core

12.1 The problem LUWs solve

A business transaction must be all or nothing. When a sales order is saved, header, items, schedule lines, partners, pricing conditions, status and change documents must all be written, or none. If the system crashes halfway, the database must not contain half an order. A Logical Unit of Work (LUW) is a set of changes that is committed or rolled back together.

12.2 Database LUW

A database LUW is what the database itself commits in one step. It ends with a database commit, either explicit (COMMIT WORK, or DB_COMMIT/cl_abap_dbconnection-style calls) or implicit. SAP performs an implicit database commit when:

  • a dialog step ends (screen displayed, message of type I or W shown, or the work process is released),
  • a synchronous or asynchronous RFC call is made (the work process is rolled out),
  • a WAIT statement runs, or CALL TRANSACTION / SUBMIT starts a new session context in some cases,
  • an HTTP or RFC response returns.

So a database LUW can never span more than one screen. A user transaction with several screens is several database LUWs.

12.3 SAP LUW

An SAP LUW is a business transaction that may span many dialog steps but is written to the database as one unit. SAP achieves this by bundling: during the dialog steps you don't write to the database directly. You register the changes, and they are executed together after COMMIT WORK, in one database LUW.

Screen 1 (dialog step) → CALL FUNCTION 'Z_UPD' IN UPDATE TASK (registered, not executed) Screen 2 (dialog step) → CALL FUNCTION 'Z_UPD2' IN UPDATE TASK (registered) Save button → COMMIT WORK │ update request written to VBHDR / VBMOD / VBDATA ▼ Update work process runs Z_UPD + Z_UPD2 in ONE database LUW │ success → DB commit failure → DB rollback + express mail + SM13 entry

12.4 Bundling techniques

Update function modules (the main one)

Create a function module with processing type Update module. It has only IMPORTING and TABLES parameters, all pass by value (no EXPORTING, since nobody waits for the result).

" Dialog program
CALL FUNCTION 'Z_SAVE_ORDER_LOG' IN UPDATE TASK
  EXPORTING is_log = ls_log.
" ... more changes ...
COMMIT WORK.                   " now the update work process executes them

" Update function module (processing type: Update module, start immediately)
FUNCTION z_save_order_log.
  INSERT zsd_order_log FROM is_log.
  IF sy-subrc <> 0.
    MESSAGE a001(zsd_msg).     " type A/X in update task: whole LUW is rolled back
  ENDIF.
ENDFUNCTION.

The parameter values are stored when the CALL is executed, not at COMMIT time. Changing the variables later has no effect.

Update types

  • V1, start immediately: time-critical, primary changes (e.g. posting the document). Executed first, in one DB LUW. Can be restarted from SM13 after an error.
  • V1, immediate start, no restart: same, but can't be restarted after errors.
  • V2, start delayed: non-critical, secondary changes like statistics (e.g. LIS). Runs after all V1 modules have succeeded, in a separate DB LUW, possibly in a V2 work process.
  • Collective run: V2 modules collected and run later by a job (e.g. for LIS with RMCEX in logistics extraction).

PERFORM ON COMMIT

PERFORM save_data ON COMMIT.            " runs at COMMIT WORK in the same work process
PERFORM undo_data ON ROLLBACK.

A form registered with ON COMMIT runs once (even if registered several times) at COMMIT WORK, before the update task modules, in the dialog work process. It uses the values of global data at commit time, not at registration. Many SAP transactions use it.

Local update

SET UPDATE TASK LOCAL. before the changes makes the update modules run in the same work process, synchronously, at COMMIT WORK. It is faster and gives immediate feedback, and is used in batch jobs and BDC (update mode L).

Transactional RFC

CALL FUNCTION ... IN BACKGROUND TASK DESTINATION ... is also bundled and sent at COMMIT WORK (module 13).

12.5 COMMIT WORK and ROLLBACK WORK

  • COMMIT WORK: closes the SAP LUW. Runs the PERFORM ON COMMIT routines, triggers the update task (asynchronous: the program continues immediately), sends the tRFC calls, and releases the SAP locks passed to the update task.
  • COMMIT WORK AND WAIT: same, but waits until the update has finished. sy-subrc <> 0 if the update failed. Use it when the next statement needs to read the saved data, e.g. creating a delivery right after an order.
  • ROLLBACK WORK: discards all registered changes in the current SAP LUW, rolls back the current DB LUW, and deletes the registered update requests and forms.

For BAPIs, BAPI_TRANSACTION_COMMIT with wait = 'X' means COMMIT WORK AND WAIT, and BAPI_TRANSACTION_ROLLBACK means ROLLBACK WORK.

Common mistake: calling COMMIT WORK inside a BAdI, user exit or update module. It breaks SAP's own LUW: half of the standard document may be saved without the rest. In update modules, COMMIT WORK isn't even allowed. Never commit inside someone else's transaction.

12.6 Update errors and SM13

If an update module fails (database error, or a message of type A/X), the whole update request is rolled back, the user gets an express mail in the SAP inbox, and the request stays in SM13 with status ERR. There you can see the failing module, its data and the error, and you can debug or repeat (for V1 restartable) after fixing the cause. ST22 shows the related dump. Update debugging: in the debugger, Settings → Update debugging, then step past COMMIT WORK.

12.7 SAP locks in detail

Database locks only last for one database LUW, which ends at every screen change. So SAP adds its own logical locks handled by the enqueue work process / enqueue server in a central lock table:

  1. When a user opens a document for change, the program calls ENQUEUE_<lock object>. If someone else holds it, FOREIGN_LOCK is raised and the user sees "Order X is being processed by user Y".
  2. The lock stays across all dialog steps.
  3. At COMMIT WORK the lock is passed to the update task (with _scope = '2', the default) and released after the update. You can also call DEQUEUE_ explicitly, or DEQUEUE_ALL.

Parameters of the ENQUEUE FM: the lock arguments (key fields, an initial value means "all values", i.e. generic lock), mode_<table>, _scope (1 = dialog only, 2 = passed to update task, 3 = both), _wait (retry for a while if locked), _collect (collect locks and send together with FLUSH_ENQUEUE).

Important: SAP locks are cooperative. They only work if every program that changes the data uses the same lock object. A Z program that updates a table without calling ENQUEUE ignores locks entirely. Locks are visible in SM12, where administrators can delete orphaned locks (carefully).

I read data after setting the lock, and I never commit inside exits or BAdIs."

Interview questions

SAP LUW vs database LUW?

A database LUW is the unit the database commits at once, and SAP issues an implicit DB commit at every screen change. An SAP LUW groups all changes of one business transaction across screens. It is achieved by collecting changes with update function modules and executing them together on COMMIT WORK, so either everything is saved or nothing is.

COMMIT WORK vs COMMIT WORK AND WAIT?

COMMIT WORK triggers the update asynchronously and the program continues at once. AND WAIT waits until the update finishes, which you need if the next step reads the data just written, e.g. after BAPI_TRANSACTION_COMMIT with WAIT = 'X'.

Why are SAP locks needed if the database has locks?

Database locks last only one DB LUW, which ends at every screen change. An SAP transaction spans several screens, so SAP uses logical locks in the enqueue server (ENQUEUE FMs) to keep a record locked across the whole SAP LUW and stop two users editing the same document.

V1 vs V2 update?

V1 updates are time-critical, run first in the update work process and can be restarted from SM13 if they fail. V2 updates run after V1 succeeds, are lower priority and are typically used for statistics. If V1 fails, V2 doesn't run.

Why can't an update function module have EXPORTING parameters?

It runs later, asynchronously in the update work process, after the calling program has continued or ended. There's nobody to receive output values, so only IMPORTING and TABLES (pass by value) are allowed.

What is the difference between PERFORM ON COMMIT and CALL FUNCTION IN UPDATE TASK?

PERFORM ON COMMIT runs in the dialog work process at COMMIT WORK, using global data values at commit time, and runs only once per form. An update FM runs in the update work process (unless local update is set), with parameter values frozen at the time of the CALL, and every call is executed.

Where do you see failed updates and how do you fix them?

SM13, filtered on status ERR. Double-click to see the failing update module, the error and the data. After fixing the cause (e.g. missing customizing), restartable V1 updates can be repeated from SM13. ST22 usually has the matching dump.

Why read data after setting the lock, not before?

If you read first and lock afterwards, another user could change the record between your read and your lock, and you would overwrite their change with stale data. Lock, then read the current version, then change.

13.2 RFC: Remote Function Call

RFC lets a program call a function module in another system, or in the same system in a separate session. The called FM must have processing type Remote-Enabled Module.

RFC destinations (SM59)

  • Type 3: ABAP connection to another SAP system (target host, system number, client, user, password or trusted relationship).
  • Type T: TCP/IP connection to an external program (registered server program).
  • Type G: HTTP connection to an external server (REST and web calls with CL_HTTP_CLIENT).
  • Type H: HTTP connection to another ABAP system.
  • Use "Connection Test" and "Remote Logon" to test. NONE is the local system, BACK is the calling system (callback).

13.3 BAPI in depth

A BAPI (Business Application Programming Interface) is a standardised, released, RFC-enabled function module that is registered as a method of a business object type in the Business Object Repository (BOR). For example, business object BUS2032 (sales order) has method CreateFromDat2, implemented by BAPI_SALESORDER_CREATEFROMDAT2. Browse them in transaction BAPI (BAPI Explorer) or SWO1.

BAPI rules (SAP's programming guidelines):

  • No COMMIT WORK inside. The caller decides, with BAPI_TRANSACTION_COMMIT, so several BAPIs can form one LUW.
  • Errors are reported in a RETURN parameter (BAPIRET2: TYPE S/I/W/E/A, ID, NUMBER, MESSAGE, MESSAGE_V1-4, PARAMETER, ROW, FIELD), never by classic exceptions or screen messages.
  • No screen output, no dialogs. Pass by value, and all parameters are DDIC-typed.
  • Stable interface across releases (released and documented).
  • Often a TESTRUN flag, X-structures, and EXTENSIONIN/EXTENSIONOUT for custom fields.

Creating your own BAPI: create an RFC FM following the rules (name ZBAPI_..., RETURN parameter, BAPI structures), create or extend a business object in SWO1 (subtype a standard object), add the method using the API function, set status to implemented and released. In practice many projects simply create RFC-enabled FMs following BAPI conventions without registering them in the BOR.

Common BAPIs: BAPI_SALESORDER_CREATEFROMDAT2, BAPI_SALESORDER_CHANGE, BAPI_PO_CREATE1, BAPI_PO_CHANGE, BAPI_GOODSMVT_CREATE, BAPI_ACC_DOCUMENT_POST, BAPI_MATERIAL_SAVEDATA, BAPI_MATERIAL_GET_DETAIL, BAPI_CUSTOMER_GETDETAIL2, BAPI_USER_GET_DETAIL, BAPI_OUTB_DELIVERY_CREATE_SLS, BAPI_BILLINGDOC_CREATEMULTIPLE.

13.4 IDocs: the concept

An IDoc (Intermediate Document) is SAP's standard message format for asynchronous data exchange. Every IDoc is stored in the database with a number, so it can be monitored, corrected and reprocessed. ALE (Application Link Enabling) is the framework for exchanging IDocs between SAP systems (and with non-SAP systems via middleware). EDI is the exchange of business documents with external partners (customers, vendors) using standards like EDIFACT or ANSI X12, often converted to and from IDocs by an EDI subsystem.

IDoc structure

  • Control record (one per IDoc, table EDIDC): IDoc number (DOCNUM), direction (1 outbound, 2 inbound), message type, basic type, extension, sender and receiver port, partner type and number, status, creation date and time.
  • Data records (table EDID4): one per segment occurrence. Each has the segment name, segment number, parent number (hierarchy) and the data in field SDATA (1000 characters), laid out according to the segment structure.
  • Status records (table EDIDS): a history of every status the IDoc went through, with messages.

13.5 ALE configuration step by step

  1. Logical systems (BD54 or SALE): define a name for each system, e.g. S4DCLNT100, LEGACY01. Assign the own logical system to the client in SCC4.
  2. RFC destination (SM59) to the partner system. For SAP to SAP, name it like the receiver's logical system.
  3. Port (WE21): a transactional RFC port pointing to the RFC destination (for SAP or middleware), or a file port (IDocs written as files), or an XML HTTP port.
  4. Distribution model (BD64): create a model view, add the message type with sender and receiver logical systems, and optionally filters (e.g. only plant 1000). Generate partner profiles from here (Environment → Generate partner profiles), then distribute the model view to the receiver.
  5. Partner profile (WE20): for partner type LS (logical system), KU (customer), LI (vendor). Inbound parameters: message type, process code, and processing (trigger immediately or by background program RBDAPP01).
  6. Process codes: outbound (WE41) for message control based IDocs, and inbound (WE42) linking to the inbound function module.

13.10 Extending a standard IDoc

  3. Link the message type, basic type and extension in WE82.

Interview questions

Explain the end-to-end configuration for an outbound IDoc.

Define logical systems (BD54) and assign them to clients (SCC4). Create an RFC destination to the receiver (SM59) and a tRFC port (WE21). Maintain the distribution model with sender, receiver and message type (BD64). Create the outbound partner profile with message type, port, IDoc type and output mode (WE20). Trigger it via change pointers (BD21), output types (NACE) or custom code with MASTER_IDOC_DISTRIBUTE. Monitor in WE02.

How do you create a custom IDoc?

Create segments in WE31, the basic type in WE30 (segment hierarchy and cardinality), the message type in WE81, and link them in WE82. For outbound, write a program that fills the control and data records and calls MASTER_IDOC_DISTRIBUTE. For inbound, write a function module with the standard interface, register it in WE57 and BD51, create a process code in WE42, and add it to the partner profile.

An inbound IDoc is in status 51. What do you do?

Read the status message in WE02 to see the application error, such as a missing master data or a locked document. If it's a data issue, fix the master data or edit the IDoc segment in WE02, which creates a backup copy, and reprocess in BD87. If it's a code issue, debug by reprocessing in BD87 with a breakpoint in the inbound FM, or copy the IDoc in WE19 and process inbound in foreground debug mode.

What is the difference between a basic type and an extension?

A basic type is the IDoc structure (SAP standard or custom). An extension adds custom segments to an existing basic type without changing it. You fill the extra segments in a user exit or BADI of the standard IDoc function module.

What are change pointers?

A way to send master data IDocs automatically when data changes. Activate them globally in BD61 and per message type in BD50. Changes are logged in BDCP2, and program RBDMIDOC (BD21) creates IDocs from the pointers, usually scheduled as a job.

sRFC vs aRFC vs tRFC vs qRFC?

sRFC waits for the result. aRFC runs in parallel and collects results with RECEIVE RESULTS. tRFC is asynchronous and guarantees execution exactly once, even if the target is down (retried from SM58). qRFC adds guaranteed order through queues. bgRFC is the modern successor to tRFC and qRFC.

BAPI vs normal RFC function module?

Every BAPI is an RFC function module, but it is also a method of a BOR business object. It follows naming and interface standards, returns errors in a RETURN table instead of raising exceptions, doesn't commit itself, and is released and stable across releases.

What is ALE and how is it different from EDI?

ALE is SAP's framework to exchange data between logically separate systems, mostly SAP to SAP within one company (e.g. master data from a central system to regional systems), using IDocs, logical systems and the distribution model. EDI is the exchange of business documents with external business partners in standard formats (EDIFACT, X12). It also uses IDocs inside SAP, but partners are customers or vendors (partner types KU/LI) and a translator converts the format.

What is the difference between message type and IDoc (basic) type?

The message type is the business meaning (e.g. ORDERS = purchase order). The basic type is the technical structure of segments (e.g. ORDERS05). One message type can be linked to several basic types or versions in WE82, and the partner profile decides which one is used.

An outbound IDoc is in status 30. What does that mean?

The IDoc was created and is ready for dispatch, but the partner profile output mode is "Collect IDocs". Program RSEOUT00 (usually a scheduled job) sends it. Either run RSEOUT00, or change the output mode to "Transfer IDoc immediately".

Where do you check when IDocs don't reach the receiving system?

On the sending side: WE02 for the IDoc status (03 means it was passed to the port). Then SM58 for tRFC errors, such as an RFC destination down, a wrong user, or a missing partner profile on the receiver. Check the destination in SM59 with a connection test. On the receiver, look in WE02 for status 56 (no inbound partner profile) or 51.

What are SYSTEM_FAILURE and COMMUNICATION_FAILURE?

Special exceptions every RFC call can raise. COMMUNICATION_FAILURE means the connection couldn't be established or broke (network, destination, logon). SYSTEM_FAILURE means a runtime error happened in the called system, such as a dump. Always handle both, with MESSAGE lv_msg to get the text.

14.1 What OData is

OData (Open Data Protocol) is a REST-based standard for reading and changing data over HTTP. Fiori apps, mobile apps and many external systems use it to talk to SAP. Every OData service has:

  • a service document listing entity sets: /sap/opu/odata/sap/ZSD_ORDER_SRV/,
  • a metadata document describing entity types, properties, keys and associations: .../$metadata,
  • entity sets (collections): .../OrderSet,
  • single entities by key: .../OrderSet('0000012345').

HTTP methods map to operations: GET = read, POST = create, PUT (full) / PATCH or MERGE (partial) = update, DELETE = delete. SAP Gateway uses OData V2 for most SEGW services. RAP supports both V2 and V4.

SAP Gateway is the component that exposes OData in ABAP. Components: IW_BEP (backend event provider, where your service code lives) and IW_FND (Gateway foundation / hub, where services are registered and called). These can run on the same system (embedded deployment, standard in S/4HANA) or on a separate hub system.

14.2 Building a service in SEGW, step by step

  1. SEGW → Create project ZSD_ORDER (type Service with SAP annotations, generation strategy Standard), with a package.
  2. Data Model → Import → DDIC Structure (e.g. a Z structure or VBAK), choose the fields, and mark the key. This creates an entity type Order and an entity set OrderSet. Do the same for Item.
  3. Create an association Order → Item (cardinality 1:N, with referential constraint VBELN = VBELN) and the navigation property ToItems.
  4. Generate runtime objects (red-white wheel). SAP creates:
    • ZCL_ZSD_ORDER_MPC and ZCL_ZSD_ORDER_MPC_EXT (model provider: metadata),
    • ZCL_ZSD_ORDER_DPC and ZCL_ZSD_ORDER_DPC_EXT (data provider: your code goes here),
    • the registered model and service in the backend.
  5. Register the service in /IWFND/MAINT_SERVICE → Add Service → system alias (LOCAL for embedded) → find your service → add it with a package.
  6. Implement methods in DPC_EXT (redefine).
  7. Test in /IWFND/GW_CLIENT (the Gateway client): enter the URI, method, request body, and look at the response.

You can also map data sources directly in SEGW: Service Implementation → Map to Data Source → a CDS view, RFC/BAPI, or search help. That generates code automatically. Or reference a CDS view as a data source (Reference → Data Source).

14.8 SEGW vs CDS / RAP services

In S/4HANA you have three ways to build OData:

  1. SEGW, code-based: full control, most code, still common in existing projects.
  2. CDS with @OData.publish: true (older S/4 releases): exposes a CDS view as a read-only service (or with BOPF for transactional), registered in MAINT_SERVICE. Now deprecated in favour of RAP.
  3. RAP: CDS data model, behavior definition, service definition (define service ... { expose ZC_Order as Order; }) and service binding (OData V2 or V4, UI or Web API). Publish from the binding. SAP's recommended model (module 17).
Say it in the interview: "In SEGW I model the entities from DDIC structures, create associations and navigation, generate, and implement GET_ENTITYSET with filter and paging, GET_ENTITY, and CREATE_DEEP_ENTITY for header-item creates in DPC_EXT. Interview questions

Why code in DPC_EXT and not DPC?

DPC is regenerated every time the model changes in SEGW, so code there would be lost. DPC_EXT inherits from DPC and is never regenerated. You redefine methods there.

How do you handle $filter in GET_ENTITYSET?

Use io_tech_request_context->get_filter( )->get_filter_select_options( ) to get select-option ranges per property, or the filter string via get_filter_string( ), and use them in your SELECT. Paging uses is_paging-top and skip.

What is a deep entity?

A create request that posts a header with its items in one call, e.g. a sales order with lines. You define a deep structure in MPC_EXT and redefine CREATE_DEEP_ENTITY in DPC_EXT.

SEGW vs CDS-based OData?

SEGW is the classic, code-heavy way. In S/4HANA you can expose CDS views via service definition and binding (RAP), or the older @OData.publish: true annotation, with much less code. RAP is SAP's recommended model for new services.

What is the difference between MPC and DPC?

MPC (Model Provider Class) defines the metadata: entity types, properties, associations, and the $metadata document. DPC (Data Provider Class) provides the data and implements CRUD and other operations. Both have _EXT subclasses that survive regeneration, where you put custom code.

How is $expand handled and how do you make it faster?

By default, the framework calls GET_ENTITY or GET_ENTITYSET for the parent and then the child entity set once per parent row, which means many calls. For performance, redefine GET_EXPANDED_ENTITY or GET_EXPANDED_ENTITYSET, read parent and children with one or two SELECTs, return a deep structure, and tell the framework which navigation paths you handled via et_expanded_tech_clauses.

What is a CSRF token in OData?

A protection against cross-site request forgery. Modifying requests (POST, PUT, PATCH, DELETE) must carry a valid token, which the client gets by sending a GET with header X-CSRF-Token: Fetch. Without it, Gateway returns 403 "CSRF token validation failed".

How do you return BAPI error messages to a Fiori app?

Add them to the message container (add_messages_from_bapi) and raise /IWBEP/CX_MGW_BUSI_EXCEPTION with that container. The app receives an HTTP 400 with the messages in the error response body, which Fiori shows in a message popover.

15.1 What SAP Business Workflow does

SAP Business Workflow automates business processes that involve people and decisions: approvals (purchase requisitions, invoices, leave requests, new vendors), notifications, and multi-step processes with escalations. The workflow engine sends work items to the right people's inboxes (SAP Business Workplace SBWP, or the Fiori app "My Inbox"), waits for their decisions, runs background steps automatically, and keeps a full log of who did what and when.

In S/4HANA there is also flexible workflow (configured by key users in Fiori apps for documents like purchase requisitions, POs and supplier invoices), and SAP Build Process Automation on BTP for side-by-side processes. Classic workflow (SWDD) remains widely used and is what most interviews focus on.

15.3 Tasks

A standard task (PFTC, type TS, number like TS90000012) wraps one method of an object type or class:

  • Object method: the object type or class plus the method, synchronous or asynchronous. Background processing means it runs as WF-BATCH automatically, with no user involved.
  • Work item text: the subject line users see in the inbox, with container variables (e.g. "Approve order &ORDER.VBELN& of &AMOUNT&").
  • Description: the long text shown in the work item preview.
  • Task container: the data the task needs, with the binding to the method's parameters.
  • Agent assignment (Additional data → Agent assignment → Maintain): possible agents, the users, roles, org units or positions allowed to execute it. Or set it as a General task, which anyone may execute (common, with responsibility controlled in the workflow step).
  • Terminating events: for asynchronous tasks, the work item completes when this event occurs (e.g. the PR is released in ME54N by any route).

15.5 Containers and bindings

A container is a set of named variables. There are several: the event container (data sent with the event, always including _EVT_OBJECT and _EVT_CREATOR), the workflow container, the task container, the method parameters and the rule container.

A binding copies values between containers. The arrows you define:

  1. Event → workflow (in start events): &_EVT_OBJECT& → &ORDER&, &EV_AMOUNT& → &AMOUNT&, &_EVT_CREATOR& → &INITIATOR&.
  2. Workflow → task (in each step): &ORDER& → &_WI_OBJECT_ID&.
  3. Task → method (in the task): parameters of the method.
  4. Back again (method → task → workflow) for results, e.g. the decision or a returned value.

Container elements must be marked Import or Export to be bindable. Most "empty value in step" problems are missing or wrong bindings, which you see in the workflow log.

15.6 Agent determination

Who gets a work item is decided in layers:

  1. Possible agents on the task (or General task).
  2. Responsible agents in the step: a rule (PFAC), an expression (container element holding a user, e.g. &INITIATOR& or &APPROVER&), or an organisational object (position, job, org unit from the organisation model, PPOME/PPOCE).
  3. Excluded agents, e.g. the requester can't approve their own document.

The recipients are the responsible agents who are also possible agents, minus the excluded ones. If none are found, the work item goes to all possible agents, or to the workflow administrator if "Terminate if rule resolution without result" is set.

Rule with function module (most common in projects): in PFAC create a rule of type "Function to be executed". The FM has the interface AC_CONTAINER (input values) and ACTOR_TAB (result), and raises NOBODY_FOUND if empty:

FUNCTION z_wf_get_approver.
*" TABLES actor_tab STRUCTURE swhactor ac_container STRUCTURE swcont
*" EXCEPTIONS nobody_found
  DATA lv_kostl TYPE kostl.
  swc_get_element ac_container 'COSTCENTER' lv_kostl.          " macro from INCLUDE <cntn01>
  SELECT SINGLE approver FROM zwf_approvers WHERE kostl = @lv_kostl INTO @DATA(lv_user).
  IF sy-subrc <> 0. RAISE nobody_found. ENDIF.
  APPEND VALUE #( otype = 'US' objid = lv_user ) TO actor_tab.
ENDFUNCTION.

Other rule types: responsibilities (maintained values per range, e.g. cost centre 1000–1999 → user A), org data, and function to be executed.

Substitution: users set substitutes in SBWP (Settings → Workflow settings → Maintain substitute) for absences, either active (receives items automatically) or passive (must adopt them). Forwarding: users can forward a work item to someone else if the task allows it.

15.7 Triggering a workflow

Workflows start from events. Ways events get raised:

  • Change documents: SWEC links a change document object (e.g. VERKBELEG for sales docs) to an object type and event, on create or change, optionally only when a specific field changes.
  • Status management: BSVW links status changes to events.
  • Message control: an output type with medium 9 (Events/SAP Business Workflow) in NACE.
  • Standard application events: many transactions raise events directly (e.g. BUS2105.RELEASESTEPCREATED in PR release strategy), and others are activated through SPRO settings.
  • Your own code (user exit, BAdI, report): with classes, CL_SWF_EVT_EVENT=>RAISE (shown above). With BOR, SAP_WAPI_CREATE_EVENT or SWE_EVENT_CREATE. Events are processed at COMMIT WORK.
  • Directly: SAP_WAPI_START_WORKFLOW starts a workflow without an event, which is useful for testing or special cases.

Event linkage (SWE2): object type, event, receiver type (the workflow), receiver function module (SWW_WI_CREATE_VIA_EVENT_IBF), optional check function module (decides at runtime whether to start the workflow, e.g. only for order type ZOR; it raises an exception to block the start), and a receiver type FM (choose which workflow to start). The linkage must be Active. Event queue settings (SWEQADM) handle high volumes.

Test an event without the application: SWUE (create event), and SWUS (start a workflow directly with container values).

15.8 Deadlines, escalation and other step settings

In each activity step, the deadline tabs are: Requested start (the work item becomes visible only then), Latest start, Requested end, and Latest end. For each, set a time relative to the work item creation, or an expression, plus an action. Either notify someone (a "missed deadline" work item to the recipient or a manager), or use a modeled deadline: an outcome branch where you add steps such as escalate to the next level or auto-reject. Deadline monitoring runs via job SWWDHEX, configured in SWU3.

Other step settings: outcomes (e.g. "Processing obsolete", "Task executed synchronously"), advance with dialog (the next dialog step for the same user opens immediately), confirm end of processing, and notification (send a mail when completed).

15.9 Example: two-level approval of a Z document

  1. Class ZCL_WF_ORDER with event CREATED (amount as parameter), methods APPROVE and REJECT, and attribute values.
  2. Raise the event from the save BAdI or your program (the raise_created method). It is delivered when the document's COMMIT WORK runs.
  3. Workflow template ZWF_ORDER_APPR: start event ZCL_WF_ORDER.CREATED, binding _EVT_OBJECT → ORDER, EV_AMOUNT → AMOUNT, _EVT_CREATOR → INITIATOR.
  4. Step 1: user decision "Approve order &ORDER.MV_VBELN&?" with Approve and Reject. Agent: rule Z_WF_GET_APPROVER with cost centre. Deadline: latest end 2 days → escalate to the manager.
  5. Condition: &AMOUNT& > 100000 → step 2: second-level user decision for the department head (from org structure).
  6. Approve branch: background activity calling task TS... (method APPROVE). Reject branch: background task REJECT, then a send mail step to &INITIATOR& with the rejection reason (from a decision note).
  7. Activate the template and check the event linkage in SWE2 is active.
  8. Test: create a document, check SWEL (event trace) to confirm the event started the workflow, find the work item in the approver's SBWP or My Inbox, and check the log in SWI1 or the workflow log (graphical).

Walk me through building a purchase-requisition approval workflow.

BOR object vs ABAP class in workflow?

BOR (SWO1) is the older, macro-based approach. Classes implementing IF_WORKFLOW (with BI_PERSISTENT~FIND_BY_LPOR and LPOR) are object-oriented, easier to debug and test, and preferred for new development.

A workflow didn't start. How do you troubleshoot?

Turn on the event trace (SWELS) and reproduce. Check SWEL: was the event raised? Was a receiver found? Check event linkage in SWE2 (active? check function blocking it? any errors?). Check the workflow is activated and that SWU3 basic setup is green. If it started but is stuck, look at SWI1 or SWIA for the work item status and error log, and restart with SWPR after fixing.

How is agent determination done?

The task's possible agents define who is allowed (or set as general task). The step's responsible agents narrow it down, using a rule (PFAC) backed by a function module or Z table, an org object (position, org unit), or an expression from the container. The final recipients are the intersection, minus excluded agents.

What are bindings?

Data flow mappings between containers: event container to workflow container (at start), workflow container to task container (when a step runs), task container to method parameters, and back. Missing or wrong bindings are a common cause of empty values in steps.

How do you debug a background workflow step?

Background steps run as user WF-BATCH. Set an external breakpoint for that user in the method, or temporarily make the step a dialog step assigned to yourself. Alternatively, execute the method directly in SWO1 or the class test in SE24 with test data.

What is the difference between a synchronous and asynchronous task?

A synchronous task completes when its method finishes and can return values directly. An asynchronous task's method only starts the action (e.g. opens a change transaction), and the work item completes when a terminating event arrives. That way it is completed however the document is processed, even by a different transaction.

What is a check function module in event linkage?

An FM registered in SWE2 that runs before the workflow starts. It reads the event container and object, and raises an exception to prevent the start when conditions aren't met, e.g. only start for document type ZOR or amounts over a limit. This avoids starting and then cancelling unnecessary workflows.

What is WF-BATCH?

The system user under which background workflow steps run and which the workflow runtime uses internally. It is set up in SWU3, needs broad authorizations (typically SAP_ALL in many projects, or a defined role), and must exist in each client where workflows run.

How do you add a custom method to a standard BOR object like BUS2105?

Create a subtype (ZBUS2105) of BUS2105 in SWO1, add the method and implement it, release it, then set up delegation (SWO1 → Settings → Delegate) from BUS2105 to ZBUS2105. Workflows that use BUS2105 then see the new method without changing the object type they reference.

What is the difference between possible, responsible and excluded agents?

Possible agents are defined on the task and say who is allowed to execute it (or everyone, for a general task). Responsible agents are defined in the workflow step and say who should get it in this case. Excluded agents are removed, e.g. the initiator. The final recipients are the responsible agents who are also possible agents, minus excluded.

16.1 What changes with SAP HANA

SAP HANA is an in-memory, column-store database. All data is held in RAM, and tables are stored column by column instead of row by row. That makes aggregations, filters and scans over millions of rows extremely fast, and it compresses data well. It also changes how good ABAP looks:

Classic database thinkingHANA thinking
Read raw data into ABAP, then calculateCode pushdown: calculate in the database, return only results
Avoid joins, prefer FOR ALL ENTRIESJoins are cheap. Prefer joins and CDS views
Aggregate tables (totals tables) for speedAggregate on the fly from line items. S/4 removed many totals tables
Secondary indexes for every slow selectRarely needed. The column store scans fast
SELECT * costs bandwidthSELECT * costs much more: every column must be reconstructed

The guidelines still apply: keep result sets small, transfer few columns, avoid many small round trips, and push logic to the database.

16.2 Tools: ADT in Eclipse

ABAP Development Tools (ADT) is the Eclipse-based IDE. You must use it for CDS views, AMDP, RAP and ABAP Cloud, because SE80 can't edit these. Setup: install Eclipse, add the ADT plug-in from SAP's tools site, then create an ABAP project with a logon to the system. 16.4 CDS views in depth

Core Data Services (CDS) let you define rich, reusable data models in the database with a SQL-like language (DDL), plus annotations that add semantics. A CDS view is consumed like a table in Open SQL, exposed via OData, used in analytics, and secured with DCL. In S/4HANA, SAP's own data model is built on thousands of CDS views (the Virtual Data Model, VDM), e.g. I_SalesOrder, I_Customer, I_Product.

  • Joins: inner, left outer, right outer, cross.

  • Parameters: define view entity ZI_X with parameters p_date : abap.dats as select ..., consumed as FROM zi_x( p_date = @sy-datum ).
  • Session variables: $session.user, $session.client, $session.system_date, $session.system_language.
  • Built-in functions: string (concat, substring, replace, length), numeric (round, div, division), date (dats_add_days, dats_days_between), conversion (unit_conversion, currency_conversion), coalesce, cast.
  • Aggregations with group by and having, and unions.
  • Calculated fields with case expressions.

16.7 Custom code migration (ECC to S/4HANA)

  1. Scope: find which custom objects are actually used, with usage data from SUSG, SCMON or UPL. Unused code is decommissioned, and in practice often 30–60% of custom code is unused.
  2. Analyse: run ATC with check variant S4HANA_READINESS (remote checks from a central check system) against the Simplification Item Catalog. Each finding points to an SAP note explaining the change.
  3. Adapt: fix findings. ADT offers quick fixes for many of them (e.g. adding ORDER BY, replacing removed tables).
  4. Optimise for HANA: use SQLM (SQL Monitor) in production to record the most expensive SQL, and SWLT (SQL Performance Tuning Worklist) to combine SQLM data with static findings, then prioritise.

HANA-specific functional issues

  • No implicit sort order: older databases often returned rows in primary key order by chance, and HANA doesn't. Code that does READ TABLE ... BINARY SEARCH, DELETE ADJACENT DUPLICATES, AT NEW or "first row" logic after a SELECT without ORDER BY can silently give wrong results. Fix with ORDER BY PRIMARY KEY or an explicit SORT.
  • Native SQL (EXEC SQL) written for Oracle or DB2 must be rewritten.
  • Database hints for the old database become useless.
  • Pooled and cluster tables became transparent, which removes restrictions but changes performance behaviour.
  • Direct writes to removed or compatibility tables fail.

16.8 HANA performance rules (SAP's "golden rules")

  1. Keep the result set small: WHERE clauses, no unnecessary rows.
  2. Minimise the amount of transferred data: only needed columns, aggregate in the database.
  3. Minimise the number of round trips: no SELECT in loops, use joins and FOR ALL ENTRIES (properly), array operations.
  4. Minimise the search overhead: index-supported WHERE clauses where still relevant.
  5. Keep load away from the database: buffer customizing tables, avoid identical selects (ST05 "identical statements" view).
Say it in the interview: "On HANA I apply code pushdown in steps: first modern Open SQL with joins and aggregations, then reusable CDS view entities with associations and DCL, and AMDP or table functions only for logic SQL can't express. In S/4 migrations I use ATC readiness checks and the simplification catalog, add ORDER BY where code relied on implicit sorting, and replace direct table access with ACDOCA, MATDOC or released CDS views."

Interview questions

What is code pushdown and how do you achieve it?

Executing calculations, aggregations and filtering in HANA instead of the application server, so less data travels and HANA's in-memory column store does the heavy work. In order of preference: modern Open SQL (joins, aggregates, CASE, expressions), then CDS views, then AMDP or CDS table functions for logic that SQL alone can't express.

CDS view vs AMDP: when do you use which?

A CDS view is declarative, reusable, can be consumed by Open SQL, OData and analytics, and supports annotations and DCL authorization. Use it by default. AMDP is imperative SQLScript for complex logic: multiple steps, temporary results, HANA-specific functions. It is HANA-only and harder to maintain. A CDS table function wraps an AMDP so it can be used like a CDS view.

Association vs join in CDS?

A join is always executed. An association is a declared relationship that becomes a join only when a consumer actually uses a field from it (path expression like _Customer.name1). That keeps views lean, and associations can be exposed for navigation in OData.

What's the difference between define view and define view entity?

The older define view creates an extra DDIC SQL view (needs sqlViewName) and has looser syntax checks. define view entity (from 7.55) has no extra SQL view, activates faster, has stricter checks and is the recommended form.

What changes in custom code when moving from ECC to S/4HANA?

Code reading removed or changed tables (e.g. BSEG aggregates, MKPF/MSEG now via MATDOC), using customer and vendor tables directly instead of Business Partner, assuming an 18-character material number, relying on implicit sort order (HANA returns no guaranteed order without ORDER BY), and native SQL for the old database. Find them with ATC S/4HANA readiness checks and fix them, prioritised by usage data from SQLM or UPL.

Why does SELECT without ORDER BY behave differently on HANA?

On older databases, results often came back in primary-key order by accident. HANA gives no guaranteed order. Code that relied on that (e.g. READ TABLE ... BINARY SEARCH without SORT, or DELETE ADJACENT DUPLICATES without SORT) can silently break. Add ORDER BY PRIMARY KEY or an explicit SORT.

What is the VDM?

The Virtual Data Model: SAP's layered set of CDS views in S/4HANA. Basic or interface views (I_) sit on the tables, composite views combine them, and consumption views (C_) serve specific apps. Released VDM views (C1 release contract) are the stable API you should read from instead of tables, especially for ABAP Cloud.

Why must AMDP parameters be passed by value and the client handled manually?

The procedure runs in the database, outside the ABAP runtime, so there are no shared ABAP memory references. Data is copied in and out. Automatic client handling is an Open SQL feature, and SQLScript doesn't have it, so you filter on MANDT yourself (or use CDS session variables and the AMDP option CDS SESSION CLIENT in newer releases).

How do you read a field of an associated CDS view in a SELECT?

With a path expression using a backslash in Open SQL: SELECT SalesOrder, \_Customer-CustomerName FROM zi_salesorder. Inside a CDS view, use dot notation: _Customer.CustomerName. The association then becomes a join (left outer join for [0..1]).

What is a compatibility view in S/4HANA?

A CDS view with the same name and structure as a removed table (e.g. MSEG, BSIS, MARD), so existing reads keep working. It calculates the old content from the new tables (MATDOC, ACDOCA). Writes aren't possible, and heavy reads can be slow, so you should migrate to the new tables or released views.

17.4 RAP behaviour features explained

  • Numbering: managed (UUID keys filled automatically), early (you assign keys in the earlynumbering_create method), or late (keys assigned just before saving in adjust_numbers, like SAP document numbers).
  • Determinations: compute values automatically. on modify runs immediately after the change, and on save runs during the save sequence. Triggered by create, update, delete or field changes.
  • Validations: check consistency on save (and in draft's Prepare). On failure, fill failed and reported, and the save is rejected.
  • Actions: custom operations (accept, reject, copy). They can have parameters (an abstract entity as input), a result, and be static or instance-bound. Factory actions create new instances (e.g. copy travel). Internal actions are callable only from inside the BO.
  • Functions: like actions but read-only, returning data.
  • Feature control: static (field ( readonly ), mandatory) or dynamic/instance (features : instance, implemented in get_instance_features), e.g. disable the Accept button when already accepted.
  • Authorization: authorization master ( global ) for create permissions, or ( instance ) for each record, implemented in get_global_authorizations / get_instance_authorizations, typically with AUTHORITY-CHECK.
  • Locking: lock master on the root (children use lock dependent). Managed BOs use the generic lock automatically, and unmanaged ones implement the lock method with ENQUEUE.
  • ETag: optimistic concurrency. If someone changed the record since you read it, the update is rejected. The total ETag is needed for draft.
  • Side effects: tell the Fiori UI which fields to reload after a change.
  • Business events: event TravelAccepted; raised with RAISE ENTITY EVENT in the saver, for event-driven integration.

17.5 Draft handling

With with draft;, users' unsaved changes are stored in a draft table (generated with a quick fix). The app can then keep work-in-progress, survive browser closes, continue on another device, and run validations at Prepare without saving. The draft actions are Edit (create a draft from active data), Activate (validate and copy the draft to active), Discard, Resume (continue an expired draft) and Prepare (run the listed determinations and validations). %is_draft in %tky tells you whether an instance is draft or active. A draft lock is exclusive for the owner for a period (default 15 minutes of inactivity), after which other users can take over.

17.7 The RAP transactional model (interaction and save phases)

INTERACTION PHASE (each request: modify / read / action) → handler methods run, data kept in the TRANSACTIONAL BUFFER (not the DB) → determinations on modify, feature control, authorization SAVE SEQUENCE (at COMMIT ENTITIES / end of OData changeset) finalize → determinations on save check_before_save → validations; any failure → whole save rejected, back to interaction adjust_numbers → late numbering save → write to DB (managed: framework does it) cleanup → clear the buffer (cleanup_finalize → if finalize/check failed)

During the save sequence after check_before_save, nothing may fail anymore. Also, no COMMIT WORK, no dialogs, and no changes to other BOs with EML outside the allowed phases.

17.8 ABAP Cloud and clean core

ABAP Cloud is the development model for cloud-ready, upgrade-stable ABAP. It is used in the BTP ABAP environment and S/4HANA Cloud, and is available on-premise from S/4HANA 2022.

  • ABAP language version "ABAP for Cloud Development": a restricted language that removes dynpro screens, WRITE lists, SAP GUI-dependent statements, direct access to SAP tables, and similar.
  • Released APIs only: you may use only SAP objects with a C1 release contract for cloud development (released CDS views like I_Product, RAP BOs like I_PurchaseOrderTP_2, classes, BAdIs). Check the API state in ADT ("Properties → API State") or the SAP Business Accelerator Hub (api.sap.com). Using unreleased objects gives a syntax error.
  • Tools: ADT only.
  • Technologies: CDS, RAP, EML, released BAdIs, business events, and side-by-side extensions on BTP.

Clean core means keeping the S/4HANA core as close to standard as possible so upgrades are smooth. Custom code uses only stable public interfaces. SAP's earlier guidance described a 3-tier extensibility model for on-premise and private cloud: tier 1 is ABAP Cloud (cloud-ready, released APIs only); tier 2 is wrappers, meaning classic ABAP classes that wrap unreleased SAP functionality, released for use by tier 1 (a "cloud API enablement" layer); tier 3 is classic ABAP, the remaining legacy code, to be minimised. In 2025 SAP refined this into clean-core levels A to D, which rate extensions from fully cloud-ready (A) to modifications (D). Both describe the same direction, so mention the idea rather than the exact labels.

Extensibility types to name: key user extensibility (custom fields and logic in Fiori apps, no ADT), developer extensibility (ABAP Cloud in the S/4 system, on-stack), and side-by-side extensibility (separate apps on SAP BTP that call S/4 via APIs and events).

Say it in the interview: "In RAP I model the business object with a root CDS view entity and compositions, define its behavior in the BDEF with determinations, validations, actions and draft, implement the logic in the behavior pool with EML, and expose a projection through a service definition and an OData V4 binding. For ABAP Cloud, I use only released C1 APIs so the extension stays clean-core and upgrade-safe."

Interview questions

What is RAP and what are its main artifacts?

The ABAP RESTful Application Programming Model, SAP's standard way to build Fiori apps and OData APIs in S/4HANA and BTP. Artifacts: CDS data model and projection views, behavior definition, behavior pool class, service definition (what to expose) and service binding (protocol and type). Preview the app via Fiori elements from the binding.

Managed vs unmanaged RAP?

Managed: the framework handles create, update, delete, locking and saving to your tables, and you add determinations, validations and actions. Unmanaged: you implement every operation and the save sequence yourself. Used when reusing existing logic, such as a legacy BAPI or function module that owns the data.

Determination vs validation vs action?

A determination computes or changes values automatically on modify or save (e.g. set status to "Open" on create). A validation checks data, usually on save, and rejects it with messages (e.g. end date before begin date). An action is an explicit operation the user or API triggers (e.g. "Accept Travel"), shown as a button in Fiori.

What is draft in RAP?

Draft lets users save work in progress without validation and continue later or on another device. RAP keeps a draft table alongside the active table and handles edit, activate and discard. It is enabled with with draft; in the BDEF.

What does "clean core" mean for an ABAP developer?

Extend S/4HANA without modifying SAP objects and using only released, stable APIs, so upgrades don't break custom code. In practice that means ABAP Cloud, RAP, released CDS views and BAdIs, and side-by-side extensions on BTP, rather than modifications, direct table access or unreleased function modules.

What is the difference between %key, %tky and %pky?

%key holds the primary key fields. %tky (transactional key) is the key plus %is_draft (and %pid for late numbering), so it identifies draft and active instances uniquely. Use it in draft-enabled BOs. %pky is the key plus %pid (preliminary ID for late numbering).

What does IN LOCAL MODE mean in EML?

It's used inside the BO's own implementation. It skips authorization checks and feature control for that call, so internal logic (e.g. a determination setting a read-only status field) can change data the user couldn't change directly.

What is the difference between composition and association in RAP CDS?

A composition defines an existential parent-child relationship inside one business object: a booking can't exist without its travel, is locked and saved with it, and is deleted with it. A normal association just links to another entity (e.g. a customer) without ownership.

What are failed, reported and mapped?

Response parameters of RAP handler methods and EML. failed lists instances whose operation failed (with a cause). reported carries messages for the UI or caller, linked to instances and fields. mapped maps the content IDs (%cid) of newly created instances to their real keys.

Why can't you use COMMIT WORK in a RAP behavior implementation?

RAP controls the transaction: changes are collected in the transactional buffer and saved by the framework in the save sequence. A COMMIT WORK inside would break the LUW and is forbidden (it causes a runtime error in strict mode). External callers use COMMIT ENTITIES.

What is a released API and how do you check it?

An SAP object (CDS view, class, interface, BAdI, RAP BO) that SAP has marked as stable for customer use under a release contract, such as C1 for cloud development. In ADT, open the object and check the API State in Properties, or search api.sap.com. In ABAP Cloud, only released objects can be used.

18.3 Performance analysis tools

ST05: SQL trace

  1. ST05 → Activate trace (SQL trace, optionally buffer, enqueue and RFC trace) for your user.
  2. Run the program in another session (keep it short).
  3. Deactivate the trace, then Display trace.
  4. Look at: the list sorted by duration, Summarize trace by SQL statement (executions, total time, records per execution), Display identical selects (the same statement with the same values executed many times, meaning missing buffering or SELECT in a loop), and the Explain plan for a statement (which index is used, full table scan or not).

Red flags: thousands of executions of the same statement (SELECT in a loop), high time per row, a full table scan on a big table, many "identical" statements, and lots of records read but few used.

SAT: ABAP runtime analysis

  1. SAT → enter the program or transaction, choose a variant (default, or with aggregation "none" for call details) → Execute.
  2. Evaluate: the Hit list (statements by gross and net time), DB tables, the Profile view, and the Call hierarchy.
  3. The ratio ABAP vs database vs system time tells you where to look. High DB time leads to ST05. High ABAP time points to nested loops, wrong table types, string processing or big copies.

SAT replaced SE30. ST12 (from SAP support tools) combines the ABAP and SQL traces in one run and is popular for production analysis.

Other tools

  • SCI (Code Inspector) and ATC (ABAP Test Cockpit): static checks for performance (SELECT in loops, missing WHERE, SELECT *, nested loops), security, syntax and naming. Projects usually require ATC with no priority 1 or 2 errors before transport release.
  • SQLM (SQL Monitor): records SQL executed in production over days or weeks, with request entry points. SWLT: the SQL performance worklist combining SQLM data and static check results.
  • SM50 / SM66: watch a running process (current program, table being read, time). ST04 / DBA cockpit: database performance. ST03N: workload statistics per transaction. STAD: statistics per dialog step. ST02: buffer statistics.
  • /SDF/MON: snapshot monitoring.

18.4 Performance tuning checklist

Database access

  1. Never SELECT inside a LOOP. Read in bulk before the loop into a sorted or hashed table, then read from memory.
  2. Select only the needed columns. No SELECT * on wide tables.
  3. Filter in the WHERE clause, not in ABAP afterwards (no "select everything then DELETE WHERE").
  4. Use index fields in WHERE, in index order, with = or IN.
  5. Prefer joins or CDS views over nested selects. With FOR ALL ENTRIES: non-empty, de-duplicated driver table, and full keys selected.
  6. Use aggregates, COUNT and EXISTS in the database instead of reading rows to count them.
  7. Use SELECT SINGLE with the full key, or UP TO 1 ROWS.
  8. Buffer small customizing tables in SE11, or cache them yourself in a static internal table.
  9. Use array operations: INSERT ... FROM TABLE, UPDATE ... FROM TABLE, instead of row by row.
  10. For huge volumes, use PACKAGE SIZE or cursors, and parallel processing.

ABAP processing

  1. Choose the right internal table type: hashed for key lookups, sorted for ranges and LOOP WHERE.
  2. Replace nested loops with sorted tables or the parallel cursor.
  3. Use field symbols (ASSIGNING) or references in loops instead of INTO, and avoid MODIFY in the loop.
  4. Use BINARY SEARCH on sorted standard tables, or secondary keys.
  5. Avoid copying big tables. Pass by reference.
  6. Use DELETE ... WHERE and APPEND LINES OF instead of loops.
  7. Don't call the same expensive FM or method repeatedly with the same input. Cache the results.
  8. Use string templates over repeated CONCATENATE in big loops.
  9. Free large tables you no longer need.

Parallel processing

For long batch jobs over independent data, such as 1 million invoices, split the data into packets and process them in parallel with aRFC (STARTING NEW TASK DESTINATION IN GROUP), the SPTA_PARA_PROCESS_START_2 framework, or several background jobs. Make sure packets don't lock the same records.

Example story (adapt to her own experience): A daily open-orders report took 45 minutes and sometimes timed out. SAT showed 85% database time. How do you debug an RFC or OData call coming from another system?

Set an external (user) breakpoint in your code for the user the call runs as, the communication or RFC user. Settings → Debugger → set user. Then trigger the call. For OData you can also replay the request in /IWFND/GW_CLIENT with your own user.

What is a watchpoint?

A debugger setting that stops execution when a variable's value changes, or meets a condition. It is useful for finding where in a large program a field gets overwritten.

How do you analyse a short dump?

Open it in ST22: read the error type (e.g. TIME_OUT, TSV_TNEW_PAGE_ALLOC_FAILED for memory, CX_SY_ZERODIVIDE, ITAB_DUPLICATE_KEY), what happened, the source code extract at the failing line, the call stack and variable values. From there, reproduce in debug and fix the root cause, not only the symptom.

How do you debug a program that runs as a background job?

For a scheduled or finished job: in SM37 select it and enter JDBG in the command field, which restarts it in dialog in the debugger. For a running job: SM50 → select its work process → Administration → Program → Debugging. You can also add an endless loop guarded by a checkpoint group or user check temporarily and attach via SM50, which is the old technique.

What is the difference between a session and an external breakpoint?

A session breakpoint works only in your current GUI session and stops your own program runs. An external (user) breakpoint is valid for all sessions of the specified user on that server for 2 hours, including calls from outside the GUI such as RFC, HTTP/OData from Fiori, and background RFC.

What are "identical selects" in ST05 and why do they matter?

The same SQL statement with the same parameter values executed more than once in the trace. They mean the program reads data it already has, usually from a SELECT in a loop or a missing cache. Removing them (buffering, reading once into an internal table) is one of the quickest wins.

What is a checkpoint group?

An object maintained in SAAB that controls statements like BREAK-POINT ID, ASSERT ID and LOG-POINT ID. You can activate it per user, server or globally, for a limited time, without changing or transporting code. It is safe to leave in production code.

How do you find which program issues a specific error message?

Get the message ID and number with F1 → technical information. Then either use the where-used list of the message in SE91, or start the debugger before the action and set a breakpoint at statement MESSAGE (or at that specific message) to stop exactly where it's raised.
